# 实战使用记录

拿它做真实开发任务，把结果记在这里——回归集量的是「能不能改对代码」，
这里量的是「能不能干活」。两者的失败模式不一样。

---

## 2026-09-12 · 第一次：更新 README

**任务**：README 还写着「设计阶段」，但项目已经能跑了。更新它——
说明实现到什么程度、三条命令怎么用、已知边界是什么。只允许改 `README.md`。

**模型**：Qwen3.8-27B-UD-IQ2_S（回归集 50/50 那个）。

**结果：失败。** 12 步撞上限，产出的 README 已撤销。

### 做对的

- 侦察到位：读了 README、列了目录、把 `run` / `serve` / `bench` 三条命令的
  实现都读了一遍，不是凭印象写。
- 自己跑命令验证（`pytest scratch_lab -q` → 5 passed）。
- diff、确认、落盘这条流程正常，产物能看清改了什么。

### 做错的

按严重程度排：

1. **编造事实**。写「llama.cpp 供应商需要 CUDA 版的 `llama-cpp-python`」——
   这个项目根本不走 llama-cpp-python，是 HTTP 调 `llama-server`。
   提示词里明明有「信息不足先查，不要猜」，它还是编了一句看起来很专业的话。
2. **整份重写丢内容**。原来那段「这个项目在解决什么」被整段删掉。
   和回归集里 `03_add_function` 同一个毛病。
3. **接地错误**。标题改成 `# scratch_lab`——它看到目录里有 `scratch_lab/`
   就拿来用了，而项目名写在 `pyproject.toml` 里（`agents-dev`）。
4. **命令示例写错**。`python -m agents_dev run "任务"`，实际要 `--goal`。
5. **撞步数上限**。前 5 步侦察，中间被下面那条假失败带偏，12 步不够用。

### 这一轮暴露的机制缺陷（已修）

**自动验证把「测试没跑成」当成了「测试没通过」。**

当时机器上有个坏掉的临时目录（沙箱留下的），pytest 收集阶段就崩了，
退出码 2。但反馈只说「测试失败，按报错改正」，模型不知道这是环境问题，
于是拿着 `PermissionError` 去查自己的改动，烧掉大约 5 步，最后什么也没查出来。

pytest 的退出码本来就区分这两件事：`1` 是测试没过（该去改代码），
`2` 是压根没跑成（改代码没用）。现在按退出码分流，后者会明确告诉模型
「这是环境问题，和你的改动无关」。

### 还没解决的（留作后续）

- **文档类任务的编造**：没有任何可执行的东西能验证一段散文写得对不对。
  回归集能挡住代码错误，挡不住这个。
- **文档上的内容丢失**：整份重写会删掉原有段落。代码任务里试过片段替换，
  结果更糟；文档任务没试过。
- **接地错误**：预取按关键词排序，而项目名（`pyproject.toml` 的 `name`）
  没有被优先送进去。`scratch_lab` 这种误用多半来自这里。

## 2026-09-12 · 第二次：同一任务，验证上一个修复

**目的**：上一轮发现「自动验证把环境故障当成代码失败」并把退出码当判据修了。
这次重跑同一道题，看修复是否成立。

### 先说结果：那条修复是错的

pytest 在这种环境下返回的是**退出码 1**，不是 2——「非 1 即环境问题」的判据
根本不会触发。我基于了错误的前提，而且是在实测里才发现的。

**重做后的判据是「报错指向哪里」**：代码问题（导入失败、语法错）会指向
工作区里的文件；环境问题（临时目录不可写、解释器坏了）指向工作区外面。
两者必须同时满足才算环境问题——光有 `PermissionError` 不够，
还得看它指的地方不在工作区里。这条判据比退出码稳，因为它依据的是
「错误发生在谁身上」而不是一个被 pytest 混用的数字。

### 修复生效了

同一道题重跑，反馈变成：

> 自动验证的结果：测试没能跑起来（报错指向的是工作区外面的东西，属于环境问题）

而且模型**没有再花步数去查 web 测试**——上一轮它为此烧掉约 5 步，
这一轮是 0 步。它直接回到正事上继续改 README。

### 修复顺带暴露的第二个问题（也已修）

环境故障在**每次编辑后都被重报一遍**，这一轮报了 7 次，每次都往上下文里
再灌一段同样的报错。模型明知道它不可行动，还是每次都收到。
现在确认一次之后就不再重跑命令，只回一句「依然是坏的，继续手头的事」。

### 这道题还是没做成，但原因换了

上一轮是被环境故障带偏，这一轮是**内容本身错了**：标题仍然写成
`# scratch_lab`，而且中途开始把 README 翻译成英文（`# A local Agent lab
that actually runs`）。12 步撞上限，产物已撤销。

验证机制帮不上这种错——没有任何可执行的东西能判断一段散文写得对不对。
这是文档类任务的固有边界，不是这一轮能修的。

### 附带：完整性测试又抓到一条坏题

`39_dedupe_order` 这道题要求「去重时保留首次出现的顺序」，而原始代码用的是
`list(set(...))`。字符串的哈希是随机的，`set` 的迭代顺序随进程变化——
**有时候它恰好等于期望顺序，这道题就「未修改就通过」了**。

它一直是不稳定的，只是今天才轮到那个哈希种子。已改成用整数做输入：
小整数的迭代顺序稳定（升序），稳定地不等于期望顺序。

## 2026-09-12 · 让独立审查真正成为闸门

**改动**：审查结论结构化（pass/fail + 理由），不通过就打回主循环，
由它决定要不要再派一次修复；循环上限 2 轮。

### 真实运行暴露的四个问题（都已修）

1. **审查者自己没跑完，被当成了「审查判定不通过」。** 它的 final 是
   「已达步数上限，任务未完成」，而判定器把这句话读成「改动不合格」——
   于是一处完全正确的实现被判死，还触发了一轮无意义的重做。
   现在区分「审查无结论」：那种情况既不否定也不确认，交用户判断。
2. **假日志**：只读角色收到「下一轮收窄为只能写」，但它根本没有写工具，
   什么都没收窄。日志说了没发生的事，这是最难查的一类。
3. **审查者把预算花在白名单外的命令上**：`grep`、`sed`、`ls`、`pwd`、
   `python -c` 连试十几次。它手里本来就有 `search_code` / `read_file`，
   只是没想到用——已在角色提示里写明。
4. **重复调用检测漏掉了交替打转**：`git status` / `git diff` 交替复读 11 步，
   每一步都和上一步不同，计数每次被重置。加了一条频率判据
   （同一个调用在最近 6 次里出现 3 次即拦），文案按实际命中的判据走。

### 已解决：待确认的改动对读文件的工具不可见

审查者最终给出了结论，但**结论是错的**——它说「三个文件均未做任何修改，
磁盘上仍是 normalize」。原因是结构性的：

- 实现者的改动是**待确认状态**，没有落盘；
- 审查者的 `read_file` / `search_code` 读的是真实文件，看到的是改之前的样子；
- 而它的 `run_command` 走试跑副本（副本里改动已应用），看到的是改之后的结果。

**同一个审查者，两套互相矛盾的世界。** 它反复翻文件，多半就是在试图调和
这个矛盾；最后它选择相信磁盘，于是判定「改动没落盘」。

这个问题不只影响审查者：主循环里模型改完再读同一个文件，看到的也是旧内容，
它会以为自己的写入没生效。

**修法**：加一层只读视图（`tools/view.py`），待确认的改动优先于磁盘。
`read_file` 读到改后的内容、也能读到还没落盘的新文件；`list_dir` 能列出它们；
`search_code` 改用改动后的文本重搜；`find_symbol` / `file_symbols` 用同一套
AST 提取器补上改动里的符号。

视图**刻意不缓存** pending：工具规格是装配时构造一次的，那时快照下来，
之后的每次写入它都看不见——表现是「刚写完读回来还是空的」，极难往这上面想。
这个坑在写测试时当场就踩到了。

**验证**：同一个审查场景，审查者从「反复翻文件直到步数上限、最后判定
改动没落盘」变成 4 步给出结论——读到新内容、跑测试 3 passed、搜 normalize
无命中，判定通过且理由具体。回归集 50/50 未受影响。

`find_callers` 随后也补上了：它要的是引用边，用同一套引用提取器在改动文本上
算是够的。实测同一场景，它从「找不到符号」变成成功返回，审查结论里多了
一条「调用链一致」的依据。

至此四个查询工具（read_file / search_code / find_symbol / file_symbols）
加 find_callers 都看得到待确认的改动，**模型眼里只剩一个世界**。
