# 按节补写，失败再改写

状态：L0.14 完成。不改生产代码，不进入 L3.1。

## 固定条件

| 项 | 值 |
|----|----|
| 模型 | 本机 llama-server，`Qwen3.8-27B-UD-IQ2_S`，`n_ctx=8192` |
| 采样 | `temperature=0`，`seed=1`。同一篇的三次 repeat 正文相同 |
| 思考 | 请求带 `enable_thinking=false` |
| 文章 | 技术说明、项目复盘、方案对比。初稿沿用已经裁好的半句 |
| 流程 | 仍是 F。每节最多补 2 次，仍不达标就整节改写并替换。一节失败不停下其他节 |
| 预算 | `OfflineTokenCounter`。判定线是 `prompt + max_tokens <= 8000` |
| 样本 | 3 篇初稿 + 105 次新请求 |

脚本和记录在 `recon/continuation-spike-12/`。日志里没有密钥，模型名记为 local。初稿没有重新生成。

这一轮只改失败路由，跑模型之前定下，跑完没有改：

- 遍历全部标题。某一节补写失败或改写失败，记在这一节上，后面的节继续。全文最后统一判定，不过就不写「完」。
- 每节最多 2 次 repair。长度仍低于 450、novelty 失败或脚手架命中，就 `rewrite_section`。输入是节标题、要点、上一节摘要、目标 500 字。输出整节，替换旧节。替换后再查这一节。
- 当前节和未开始的节用同一套。`anchor_lost` 仍先改写当前节，不从尾部接。改写通过也不代替全文判定。

450 字和 3000 字沿用上一轮。脚手架仍只认行首标签。可读性仍是同一个人按 L0.3 的尺子打的，不是盲评。

脚本自检覆盖了：补了 1 次仍短就再补；第 2 次失败或仍短就改写；「改法」失败之后「下一步」仍会进入补写。2000 个「甲」仍按 2000 token 计。

## 脚手架和锚点

脚手架命中 9 次，都在项目复盘的「改法」。两次补写把「要点：」「目标剩余字数：」写进返回，整段拒绝。改写的第一次返回也以「要点：」开头，整段拒绝。重试没有标签，595 字替换了旧节。正文里没有这些标签。

`anchor_lost` 仍是 3 次，都是项目复盘的重试从「范模型的输出」另起。这段没有进入正文。「过程」被改写替换，和旧正文、要点的重叠都是 0。没有未恢复的锚点。

## 预算

105 次请求全部满足 `prompt_tokens + max_tokens <= 8000`。最大合计是 4804。`OfflineTokenCounter` 比服务端 prompt 多 2 到 128 token，平均多 42.3，没有一次估小。

这 105 次合计 40089 token，耗时 643.7 秒。被拒绝的补写、思考段和脚手架都算在里面。

没有改产品代码，没有重跑 pytest。
