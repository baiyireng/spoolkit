# 工作区与会话内核 —— 设计文档

日期：2026-09-24
状态：待评审

---

## 1. 为什么做这一件事

项目的目标是一个能独立处理中小型任务的 harness，同时能配合 Codex / Cursor
这类 Agent 一起做大任务。入口面已经有四个（CLI、网页壳、聊天通道、MCP），
但**"我在哪个工作区、哪条会话里干活"这件事，四个入口各有各的答案**——
而且答案都在进程启动那一刻定死。

真实的使用体验是：手机上的机器人绑在一个工作区上，想让它去另一个项目干活，
要杀进程、重敲一条带 `--root` 的长命令、让对方重新发消息拿配对码、再在新工作区
里批准一遍。这条流程在文档里被写成"显式重启 + 重新配对"，理由是"记忆、索引、
检查点、授权范围都跟着工作区走"。理由成立，但代价是把复杂度推给了人，而且**是
结构性的**——每加一个入口就多一份"启动时钉死 root"的代码。

同类产品的形状是清楚的：Cursor 是"窗口 = 项目，项目里有多个对话"；Codex 是
"任务属于项目"。也就是**工作区（项目）与会话（对话）是两层，入口面只是这两层
的客户端**。本项目缺的正是这一层。

目标：

- 工作区与会话有明确的生命周期，能在运行时列、选、建、切，不需要重启进程。
- 四个入口共用同一份解析逻辑，不再各自解析 `--root`。
- 放行（谁能驱动）与工作区解耦，换工作区不再需要重新配对。
- 网页壳从"三个按钮的薄壳"变成对话面：页面结构像 ChatGPT／千问，
  能靠说话触发的事就别做成按钮。

---

## 2. 现状的破绽

三处结构性问题，都不是"漏了一个功能"。

### 2.1 绑定是启动参数，不是状态

`spool bridge` / `spool mcp` / `spool serve` / `spool hub` 都在进程起来那一刻
把 root 钉死（`Path(args.root).resolve()` 之后一路传下去）。CLI 有
`workspace.resolve_root` 那套"显式 → 向上找 → 登记表 → 当前目录"的解析，
**但那套逻辑只有 CLI 用得上**。

### 2.2 放行挂在工作区里

`pairing.py` 把已批准的人和待批准的码写在 `.agent/bridge-pairings.json`——
工作区级。文件里连"是哪个通道"都没有，因为一条桥进程本来就是一条通道、
一个工作区。于是"信任"和"地点"绑死：换工作区 = 重新配对。

### 2.3 会话有概念、没生命周期

`.agent/sessions/<会话>/`（plan / progress / tasks）、`memory.db` 里的会话表、
`spool session` 列表都已经在了。但会话只在启动时用 `--session` 选一次，
而且被各入口硬编码了不同的默认名（`cli` / `chat` / `bridge` / `mcp`）。

后果：**一个工作区本该有多个会话，而 QQ 那条通道把所有聊天塞进同一个
`bridge` 会话**；`spool session` 列出来的名字（`cli`、`bridge`）也看不出
各自是干什么的。

---

## 3. 核心决策

### 3.1 文件派：登记表 + 指针是唯一真相，不引入守护进程

三种做法里选最简单的：

| 做法 | 长什么样 | 代价 |
|---|---|---|
| **文件派（选它）** | 登记表 + 指针文件是唯一真相；四个入口读同一份；切换 = 改一个指针 | 没有集中调度；多入口并发靠文件锁 + "同工作区同时只跑一轮"兜住 |
| 守护进程派 | hub 变成常驻内核，所有入口走 HTTP 连它 | CLI 从此离不开 hub，而"没起 hub 也能用"是现在真实的好处 |
| 混合 | 文件为准，hub 在跑时额外提供订阅 | 两条路都得维护 |

关键理由是**接口不变**：哪天真的需要并发与多客户端订阅，把内核的实现从文件换成
服务即可，入口面一行不用改。

机器级状态放现有状态目录（`workspace.state_dir()`，`SPOOLKIT_STATE` 可覆盖）：

```
<state_dir>/workspaces.json      工作区登记表（已有，格式不变）
<state_dir>/clients.json         客户端指向
<state_dir>/channel-trust.json   放行：谁 + 能碰哪些工作区
```

### 3.2 对象模型

| 概念 | 是什么 | 落在哪 |
|---|---|---|
| **工作区** | 带 `.agent/` 的目录。身份 = 规范化路径；显示名取目录名，重名带父目录后缀；可设别名 | `workspaces.json` + `.agent/` |
| **会话** | 属于某个工作区的一条活：id、标题、模型、创建与最近活跃 | `memory.db` 会话表 + `.agent/sessions/<id>/` |
| **客户端指向** | 某入口"现在指着哪儿" = 一对 (工作区, 会话) | `clients.json` |
| **放行** | 谁能驱动 + 能碰哪几个工作区 | `channel-trust.json` |

切换工作区就是**换一整套工作区级状态**：策略、标定值、记忆、索引、关联目录、
放行范围全跟着走。这不是副作用，是"会话属于工作区"的下半句——所以入口面在切
之前要把当前工作区显示清楚，不能让人不知道自己现在在哪。

### 3.3 会话属于工作区，标题自动生成

跟 Codex 的"线程属于项目"一致，所以换的是 (工作区, 会话) 这一对，不是孤立的
"当前目录"。

这层归属**天然成立**：每个工作区一份 `.agent/memory.db`，会话表就在里面
（`check_binding` 已经在防"同一个会话名在两个工作区里跑"）。所以不需要额外
隔离，只需要把"选会话"和"建会话"做成显式动作。

标题默认取这条会话收到的**第一句目标**，截断（40 字）后写入；已有标题不再覆盖，
要改用 `rename`。这样列表才有意义——现在列出来的 `cli` / `bridge` 看不出内容。

**标题与归档标记落在 `.agent/sessions/<id>/meta.json`**，不改 `memory.db` 的表
结构：那里面装着真实数据，而 `.agent/sessions/` 本来就是"会话级状态"的地盘
（`plan.json` / `progress.md` / `tasks/` 都在那儿）。`create_session` 同时往
`memory.db` 落一行（复用现有的 touch），这样新会话立刻出现在列表里、也占住名字。

### 3.4 会话只在显式动作下新建

解析顺序是：显式 `--session` > 客户端指向 > **该入口沿用至今的默认名**
（`cli` / `chat` / `bridge` / `mcp`——留着它们，老会话与老计划才接得上）。
**没有"最近活跃"这层魔法，也不会自动新建**：因为 `spool run --goal …` 是一次性
任务，自动新建会让会话列表被几百条一次性运行淹掉。

新建只由显式动作触发：`spool session new`、网页的"新对话"、聊天里的 `/new`
（CLI 对话里也能 `/new`）。

`/use latest` 之类的"选最近一条"放在**选择**侧，不放在解析侧。

**一处例外要说清楚**：聊天通道第一次收到消息时，那条聊天还没有会话——由入口面
**显式建一条**（标题 = 第一句目标），因为"一个聊天 = 一条线程"是聊天这类界面的
预期形状，也是"一个工作区多个会话"真正落地的地方（见 5.2 / 5.3）。这是入口面的
动作，不是解析器偷偷新建。

### 3.5 分辨率里，"我在哪个目录"仍然比"我上次选过谁"更硬

这条容易搞反，写死：

```
CLI：   显式 --root
      > 当前目录向上找 .agent/
      > 客户端指向（clients.json 的 cli 项）
      > 登记表里唯一 / 最近使用的那一个
      > 当前目录（保持今天的行为，交给具体命令报它自己的错）
```

"向上找"必须排在指针前面：在项目子目录里敲命令，指定性明显强于"我上次在别处
`spool ws use` 过谁"。今天的 `resolve_root` 顺序正是前两条，我们只是**在它后面
接上指针**。

### 3.6 显式参数永远赢，而且不写指针

`--root` / `--session` 的语义从"钉死"改成"这一次覆盖"，并沿用现有注释里的原则
——**指定就是指定，不去改它**：显式给的值不写进指针，但登记表照旧更新最近使用
顺序。

### 3.7 放行从工作区级升到身份级

一条放行记录 = **(通道, 用户, 能碰的工作区列表)**。

- 批准时**必须点名工作区**，默认只给当时这一个。想多给就再批一次。
- 同一台机器上 QQ 的 openid 与 Telegram 的 user id 不是一套命名空间，所以通道
  必须进主键——旧文件里没有这个维度（见 6.1）。
- 桥的准入判定分两步：这个人被放行吗 → 这条消息要落到的工作区在他的列表里吗。
  不在就回一句说明，**不进 agent**。
- `allowlist` / `open` 两档保留，语义不变。

### 3.8 边界：工作区只能由人建立

`.agent/` 里装着授权策略。让 Agent 自己建工作区，等于让它给自己开辟新的信任边界。

**Agent 只能在已登记的工作区里选。** MCP 那边也一样：Codex 想在一个还没
`.agent/` 的仓库里干活，得先让你 `spool ws add <路径>` 一次。

### 3.9 人专属动作与"靠说话就能触发"的边界

用户的要求是"主要功能都能通过会话指挥 Agent"，但有一类事不能交给模型：

| 事 | 为什么不能给模型 |
|---|---|
| 批准配对 / 改放行范围 | 模型不能给自己发许可证 |
| 改授权档位与 scope | 同上（`autonomous` 那句注释已经写死了这条） |
| 关联工作区外的目录 | 同上 |
| 回滚上一次写入 | 落盘与否是人的决定 |

这四件事在网页上是**人专属按钮**，不是被砍掉的功能模块。其余能力（自主编排、
续跑、看配置、看诊断结论）都走会话。

其中"自主编排"需要一个**模式开关**（形状类似 ChatGPT 的深度研究按钮）：因为
`--autonomous` 是入口面给的模式，而且强制要求你给 `--scope`——这不是模型能自己
决定的。开关打开 = 这次运行走 `--autonomous` 那条路。

安全约束：网页的人专属动作**只在本机监听时开放**（`127.0.0.1` / `::1`）。
绑到非环回地址时默认只读（`/run` 也一并关掉），要开必须显式
`--allow-remote-control`，并在启动时打一行警告。今天绑 `0.0.0.0` 会把 `/run`
直接暴露出去，顺手收掉。

### 3.10 这一期不做跨会话并发

网页壳一次仍只跑一轮（同一个 `Runner`），会话之间可以切。

理由与"一次只跑一个运行"那条设计相同：记忆库、检查点、索引都在工作区里，
"同一工作区同时跑两轮"要处理的是合并与归属，不是 UI 问题。

## 4. 内核接口

新建 `spoolkit/kernel/`，四个小模块各管一件事，对外只暴露一个解析入口。

### 4.1 模块

```python
# kernel/workspaces.py
list_workspaces() -> list[Workspace]        # 最近使用在前
resolve_workspace(name_or_path) -> Path     # 别名 / 目录名 / 序号（1 起）/ 路径 / 向上找
register(root) -> None                      # 已有逻辑搬过来
forget(root) -> None                        # 从登记表摘掉（不删目录、不删 .agent）
set_alias(root, alias) -> None

# kernel/sessions.py
list_sessions(root) -> list[Session]        # 已有 memory.list_sessions + 标题
create_session(root, title="") -> str
resolve_session(root, name) -> str          # id / 序号 / "latest"
rename_session(root, session_id, title) -> None
archive_session(root, session_id) -> None
ensure_title(root, session_id, first_goal) -> None

# 归档 = 从默认列表里隐藏（写进 meta.json）；计划、进度、检查点、记忆都不动，
# 也仍然可以直接 use 进去。要列出来加 --all。

# kernel/pointers.py
get(client_key) -> Target | None
set_pointer(client_key, root, session) -> None
# client_key: "cli" / "web" / "chat:<通道>:<用户>" / "mcp"

# kernel/trust.py
list_grants() -> list[Grant]                # (通道, 用户, 工作区列表, 备注, 来源)
grant(channel, user, roots) -> None         # roots 必须显式给，不给就是调用错误
revoke(channel, user) -> None
allowed_roots(channel, user) -> tuple[Path, ...]
adopt_legacy(root, channel) -> int          # 认领旧配对文件，返回认领条数
```

### 4.2 唯一解析入口

```python
resolve_target(*, workspace=None, session=None, client="cli") -> Target
```

工作区按 3.5 的优先级；会话按 3.4 的优先级。返回的 `Target` 带上"这个值是从哪
来的"（显式 / 向上找 / 指针 / 登记表），因为**开局那一眼必须说清楚现在连的是
哪儿、为什么是它**——今天 `chat` 的 `_status_line` 已经在做这件事，新入口要
一样做到。

### 4.3 兼容壳

`spoolkit/workspace.py` 保留，从内核转出 `find_root` / `known` / `register` /
`resolve_root` / `state_dir` / `registry_path` / `WorkspaceError`，免得打断既有
导入路径与测试（改名那次就是这么做的）。`session_state.py` 同样保留。

## 5. 四个入口面

### 5.1 CLI

新增 `spool ws`（`workspace` 也认）：

| 子命令 | 做什么 |
|---|---|
| `spool ws` | 列出登记表（最近使用在前，标出当前那个）|
| `spool ws use <名字\|序号\|路径>` | 写 `cli` 指针 |
| `spool ws add <路径>` | 建 `.agent/` 并登记（等价 `spool init`，两个都留）|
| `spool ws forget <名字>` | 从登记表摘掉 |
| `spool ws alias <名字> <别名>` | 起别名，免得记长路径 |

`spool session` 扩成有生命周期的：`list`（默认）/ `new [标题]` / `use <id\|序号\|latest>` /
`rename <id> <标题>` / `archive <id>`。保留 `--root`。

`spool` 与 `spool chat` 开局那一眼改成显示**工作区 + 会话 + 会话标题 + 值从哪来**。
chat 里加 `/ws`、`/ws use`、`/new`、`/sessions`、`/use`。

`spool approve` 保留，但**不再需要 `--root`**：配对码本身就带着它请求的是哪个
工作区、哪条通道（见 6.1）。

### 5.2 聊天通道

`--root` 从"决定服务谁"变成**可选**：

- 不给 = 服务整台机器（用户被放行到哪些工作区，由放行记录决定）；
- 给了 = 限定在这一个工作区（向后兼容，也是给想收紧的人留的口子）。

斜杠命令扩到：`/ws`（列我能碰的工作区 + 当前）、`/ws use <名>`、`/new [标题]`、
`/sessions`、`/use <id\|序号\|latest>`、`/status`（当前工作区 + 会话 + 我能碰的）、
`/help`。

指针按**每个聊天**分键：`chat:<通道>:<用户>`。所以你在两个群里可以各自指着
不同的工作区，互不影响。

桥不再硬编码会话名。某条聊天第一次发消息、而指针里还没有会话时，由桥显式建一条
（标题 = 第一句目标）；`/new` 再开一条，旧的用 `/sessions` + `/use` 回去。

### 5.3 网页壳

结构改成对话面：

```
┌──────────────────────────────────────────────────────────┐
│ [工作区 ▾] [会话 ▾] [＋ 新对话]              [自主排程 ▢] │
├──────────────────────────────────────────────────────────┤
│  你：把 calc.py 里 sum_to 少算一个的问题修掉              │
│  ┌ 助手（12 步 · 2 次工具调用）─────────── 点开看细节 ┐  │
│  │ 改完了。验收：pytest 3 passed                     │  │
│  └──────────────────────────────────────────────────┘  │
│  ┌ 待确认：calc.py  ──────────  [应用] [拒绝] ┐         │
├──────────────────────────────────────────────────────────┤
│  > ______________________________________________         │
└──────────────────────────────────────────────────────────┘
```

- 顶部一行是选择器；切换会写 `web` 指针，刷新页面还在原处。
- 指针里没有会话时，页面显示成一条新对话；输入第一句话时用 `POST /session/new`
  显式建一条，标题取那句话。
- 对话流按消息成块，步骤 / 工具调用默认收在块里，点开看。现在的平铺日志
  （"── 第 3 步"、一行一个工具）不删，收进块内。
- 待确认 / 待批准只在出现时浮出来；`wait` 心跳（模型生成中）在块里显示一行灰字。
- 接口：`/state` 增加 `workspaces`（列表 + 当前）与 `sessions`（当前工作区的）；
  新增 `POST /target`（切工作区或会话）与 `POST /session/new`；人专属动作新增
  `POST /grant`（批准 / 拒绝配对）与 `POST /policy`。**非环回监听时全部 POST
  关闭**（含 `/run`，见 3.9），要开得显式 `--allow-remote-control`。

### 5.4 MCP

- `delegate_task` 增加可选 `workspace` / `session`。
- 新增只读工具 `list_workspaces` / `list_sessions`，让调用方先看有什么再点名。
- `spool mcp` 不再需要 `--root`；某次调用不给 `workspace` 时用 `mcp` 指针，
  指针为空而登记表里有多个工作区，就**列出候选并要求点名**（沿用现有
  `WorkspaceError` 那种"说不清是哪一个"的报错形状）。

## 6. 迁移

### 6.1 旧配对文件

`.agent/bridge-pairings.json` 的形状是 `{approved: [...], codes: {码: 用户}}`，
**没有通道维度**。所以认领要由那条通道自己来做：桥启动时用
`adopt_legacy(root, channel)` 把旧记录合成机器级放行（范围 = 那个工作区），
并打一行"已从旧记录认领 N 条放行"。

- 原文件**不删**：`spool ws forget` 只管登记表，不碰配对；配对的管理入口仍然是
  `spool approve`（`--list` / `--revoke` / `--forget`，保留）。
- 同时服务多条通道时，每条各自认领自己工作区里的旧记录，互不串。
- 待批准的码一并读进机器级（key 带上它请求的工作区）；`spool approve <码>`
  在两个地方找。

### 6.2 不动的东西

| 旧的东西 | 怎么处理 |
|---|---|
| `workspaces.json` | 格式不变，继续用；解析逻辑搬进内核 |
| 旧会话名（`cli` / `chat` / `bridge` / `mcp`）| 继续是合法会话 id，列得出来、能续，旧计划与检查点都还在 |
| `.agent/policy.json` / `limits.json` / `read-roots.json` | 不动，仍然工作区级 |
| 正在跑的桥 / hub | 改完要重启（长驻进程不自动加载新代码）；重启后不需要 `--root` |

## 7. 出错与兜底

- **登记表坏了 / 指针坏了**：当作空的——它们是便利，不是数据。显式参数照旧有效。
- **指针指向的工作区不在了**：跳过它、继续按 3.5 的顺序退（登记表 → 当前目录）；
  并在开局那一眼说明"上次指向的 X 不在了"，不静默换地方。
- **会话 id 不存在**：报错并列出该工作区的会话，不偷偷新建（悄悄新建会让
  "我的计划去哪了"变成最难查的那类问题）。
- **放行记录里某个工作区不存在了**：列出来时标出来，按"够不到"处理，不崩。
- **并发写同一个文件**：机器级文件的写入是"读-改-写 + 进程内锁 + 写临时文件再
  原子替换"。**不做跨进程文件锁**：改这些文件的动作（切工作区、批准放行）都是人
  在按，本来就不是并发写，为此引入一套锁协议不划算。链路上任何一处失败都不能
  挡住干活（沿用 `workspace.register` 现在的态度：登记不上不该挡住干活）。

## 11. 明确不做

- **不做守护进程**：CLI 不依赖 hub 这条性质要保住。
- **不让 Agent 建工作区、改放行、改授权、批越界写入**（见 3.9）。
- **不做跨会话并发**（见 3.10）；也不做"某个会话现在是否在跑"的跨进程探测。
- **不给会话做数据库迁移**：`memory.db` 的表结构不动，标题与归档标记走
  `.agent/sessions/<id>/meta.json`。
- **不动** `--events` 的既有事件语义（只增不改）；不动授权三档；不动 agent 的
  工具表（新增的 `list_workspaces` / `list_sessions` 是给 MCP 调用方的，
  不进 agent 的工具表）。
- **不碰** weft / 多模态 / T8 / 向量库；不做多用户、不做协作。
- **不重写** `web/runner.py`：它已经是四个入口共用的"跑一轮"，只是被喂的参数
  从启动参数换成 `Target`。
