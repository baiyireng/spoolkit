# 实战使用记录

拿它做真实开发任务，把结果记在这里——回归集量的是「能不能改对代码」，
这里量的是「能不能干活」。两者的失败模式不一样。

---

## 2026-09-12 · 第一次：更新 README

**任务**：README 还写着「设计阶段」，但项目已经能跑了。更新它——
说明实现到什么程度、三条命令怎么用、已知边界是什么。只允许改 `README.md`。

**模型**：Qwen3.8-27B-UD-IQ2_S（回归集 50/50 那个）。

**结果：失败。** 12 步撞上限，产出的 README 已撤销。

### 做对的

- 侦察到位：读了 README、列了目录、把 `run` / `serve` / `bench` 三条命令的
  实现都读了一遍，不是凭印象写。
- 自己跑命令验证（`pytest scratch_lab -q` → 5 passed）。
- diff、确认、落盘这条流程正常，产物能看清改了什么。

### 做错的

按严重程度排：

1. **编造事实**。写「llama.cpp 供应商需要 CUDA 版的 `llama-cpp-python`」——
   这个项目根本不走 llama-cpp-python，是 HTTP 调 `llama-server`。
   提示词里明明有「信息不足先查，不要猜」，它还是编了一句看起来很专业的话。
2. **整份重写丢内容**。原来那段「这个项目在解决什么」被整段删掉。
   和回归集里 `03_add_function` 同一个毛病。
3. **接地错误**。标题改成 `# scratch_lab`——它看到目录里有 `scratch_lab/`
   就拿来用了，而项目名写在 `pyproject.toml` 里（`agents-dev`）。
4. **命令示例写错**。`python -m agents_dev run "任务"`，实际要 `--goal`。
5. **撞步数上限**。前 5 步侦察，中间被下面那条假失败带偏，12 步不够用。

### 这一轮暴露的机制缺陷（已修）

**自动验证把「测试没跑成」当成了「测试没通过」。**

当时机器上有个坏掉的临时目录（沙箱留下的），pytest 收集阶段就崩了，
退出码 2。但反馈只说「测试失败，按报错改正」，模型不知道这是环境问题，
于是拿着 `PermissionError` 去查自己的改动，烧掉大约 5 步，最后什么也没查出来。

pytest 的退出码本来就区分这两件事：`1` 是测试没过（该去改代码），
`2` 是压根没跑成（改代码没用）。现在按退出码分流，后者会明确告诉模型
「这是环境问题，和你的改动无关」。

### 还没解决的（留作后续）

- **文档类任务的编造**：没有任何可执行的东西能验证一段散文写得对不对。
  回归集能挡住代码错误，挡不住这个。
- **文档上的内容丢失**：整份重写会删掉原有段落。代码任务里试过片段替换，
  结果更糟；文档任务没试过。
- **接地错误**：预取按关键词排序，而项目名（`pyproject.toml` 的 `name`）
  没有被优先送进去。`scratch_lab` 这种误用多半来自这里。

## 2026-09-12 · 第二次：同一任务，验证上一个修复

**目的**：上一轮发现「自动验证把环境故障当成代码失败」并把退出码当判据修了。
这次重跑同一道题，看修复是否成立。

### 先说结果：那条修复是错的

pytest 在这种环境下返回的是**退出码 1**，不是 2——「非 1 即环境问题」的判据
根本不会触发。我基于了错误的前提，而且是在实测里才发现的。

**重做后的判据是「报错指向哪里」**：代码问题（导入失败、语法错）会指向
工作区里的文件；环境问题（临时目录不可写、解释器坏了）指向工作区外面。
两者必须同时满足才算环境问题——光有 `PermissionError` 不够，
还得看它指的地方不在工作区里。这条判据比退出码稳，因为它依据的是
「错误发生在谁身上」而不是一个被 pytest 混用的数字。

### 修复生效了

同一道题重跑，反馈变成：

> 自动验证的结果：测试没能跑起来（报错指向的是工作区外面的东西，属于环境问题）

而且模型**没有再花步数去查 web 测试**——上一轮它为此烧掉约 5 步，
这一轮是 0 步。它直接回到正事上继续改 README。

### 修复顺带暴露的第二个问题（也已修）

环境故障在**每次编辑后都被重报一遍**，这一轮报了 7 次，每次都往上下文里
再灌一段同样的报错。模型明知道它不可行动，还是每次都收到。
现在确认一次之后就不再重跑命令，只回一句「依然是坏的，继续手头的事」。

### 这道题还是没做成，但原因换了

上一轮是被环境故障带偏，这一轮是**内容本身错了**：标题仍然写成
`# scratch_lab`，而且中途开始把 README 翻译成英文（`# A local Agent lab
that actually runs`）。12 步撞上限，产物已撤销。

验证机制帮不上这种错——没有任何可执行的东西能判断一段散文写得对不对。
这是文档类任务的固有边界，不是这一轮能修的。

### 附带：完整性测试又抓到一条坏题

`39_dedupe_order` 这道题要求「去重时保留首次出现的顺序」，而原始代码用的是
`list(set(...))`。字符串的哈希是随机的，`set` 的迭代顺序随进程变化——
**有时候它恰好等于期望顺序，这道题就「未修改就通过」了**。

它一直是不稳定的，只是今天才轮到那个哈希种子。已改成用整数做输入：
小整数的迭代顺序稳定（升序），稳定地不等于期望顺序。

## 2026-09-12 · 让独立审查真正成为闸门

**改动**：审查结论结构化（pass/fail + 理由），不通过就打回主循环，
由它决定要不要再派一次修复；循环上限 2 轮。

### 真实运行暴露的四个问题（都已修）

1. **审查者自己没跑完，被当成了「审查判定不通过」。** 它的 final 是
   「已达步数上限，任务未完成」，而判定器把这句话读成「改动不合格」——
   于是一处完全正确的实现被判死，还触发了一轮无意义的重做。
   现在区分「审查无结论」：那种情况既不否定也不确认，交用户判断。
2. **假日志**：只读角色收到「下一轮收窄为只能写」，但它根本没有写工具，
   什么都没收窄。日志说了没发生的事，这是最难查的一类。
3. **审查者把预算花在白名单外的命令上**：`grep`、`sed`、`ls`、`pwd`、
   `python -c` 连试十几次。它手里本来就有 `search_code` / `read_file`，
   只是没想到用——已在角色提示里写明。
4. **重复调用检测漏掉了交替打转**：`git status` / `git diff` 交替复读 11 步，
   每一步都和上一步不同，计数每次被重置。加了一条频率判据
   （同一个调用在最近 6 次里出现 3 次即拦），文案按实际命中的判据走。

### 已解决：待确认的改动对读文件的工具不可见

审查者最终给出了结论，但**结论是错的**——它说「三个文件均未做任何修改，
磁盘上仍是 normalize」。原因是结构性的：

- 实现者的改动是**待确认状态**，没有落盘；
- 审查者的 `read_file` / `search_code` 读的是真实文件，看到的是改之前的样子；
- 而它的 `run_command` 走试跑副本（副本里改动已应用），看到的是改之后的结果。

**同一个审查者，两套互相矛盾的世界。** 它反复翻文件，多半就是在试图调和
这个矛盾；最后它选择相信磁盘，于是判定「改动没落盘」。

这个问题不只影响审查者：主循环里模型改完再读同一个文件，看到的也是旧内容，
它会以为自己的写入没生效。

**修法**：加一层只读视图（`tools/view.py`），待确认的改动优先于磁盘。
`read_file` 读到改后的内容、也能读到还没落盘的新文件；`list_dir` 能列出它们；
`search_code` 改用改动后的文本重搜；`find_symbol` / `file_symbols` 用同一套
AST 提取器补上改动里的符号。

视图**刻意不缓存** pending：工具规格是装配时构造一次的，那时快照下来，
之后的每次写入它都看不见——表现是「刚写完读回来还是空的」，极难往这上面想。
这个坑在写测试时当场就踩到了。

**验证**：同一个审查场景，审查者从「反复翻文件直到步数上限、最后判定
改动没落盘」变成 4 步给出结论——读到新内容、跑测试 3 passed、搜 normalize
无命中，判定通过且理由具体。回归集 50/50 未受影响。

`find_callers` 随后也补上了：它要的是引用边，用同一套引用提取器在改动文本上
算是够的。实测同一场景，它从「找不到符号」变成成功返回，审查结论里多了
一条「调用链一致」的依据。

至此四个查询工具（read_file / search_code / find_symbol / file_symbols）
加 find_callers 都看得到待确认的改动，**模型眼里只剩一个世界**。

## 2026-09-12 · 诊断通道：让 Agent 能申请真实环境验证

**动机**：Agent 能判断出「这看起来是环境问题」——实测它说过「PermissionError
指向工作区外，属环境问题，与本次改动无关」——但没有任何办法去**证实**它，
只能干看着。

**机制**（两条规矩落在代码上，不是提示词里）：

1. Agent 只能**申请**（`request_diagnosis`）和**读回**（`read_diagnosis`）。
   报告由特权侧写（`agents-dev diagnose --report`），带 HMAC 签名。
   读的时候验签，没签名或签名不对就标成「来源无法验证」并判 ok=False。
2. **签名密钥放在项目目录之外**（`~/.agents-dev/diagnosis.key`）。
   Agent 的文件工具锁在项目根目录里，够不到它；工具代码本身能读到，用来验签。

   少了这两条，模型完全可以自己捏一份「环境有问题，忽略那些失败」再据此行动——
   那就是把编造换了个地方发生，而编造正是前面几轮反复出现的失败模式。

**实测：通道本身两个方向都通。**

- 特权侧真去查了两条证据再写报告：对该目录 `icacls` 报 Access is denied；
  换一个 basetemp 跑同一套测试得到 768 passed。
- Agent 读回报告后，把根因、证据、处理建议一字不差地转述出来了。

**但有一个必须记下的发现：模型不会主动用这个通道。**

让它「查清测试为什么跑不起来」，它做了十步：跑测试（超时）、逐个目录翻、
读 pyproject.toml，然后**去改 pyproject.toml 试图绕过**——一次都没调用
`request_diagnosis`。而自动验证的反馈里明明写着「如果确实需要查清是什么坏了，
用 request_diagnosis 登记」。这和前面几轮反复验证过的规律一致：
**这个模型对文提醒不敏感，得由循环替它做。**

（另一次运行里它没申请是合理的：那次任务成功了，没什么要查的。）

### 触发语义：先自己想办法，真卡住了才查

按「Agent 先尝试别的方案；只有确实因环境问题做不下去时才诊断」实现。
触发条件三条**同时**成立才登记：

1. 任务没做成——自己绕过去了就不必查环境；
2. 这一步确认过是环境问题（验证器给出的判定，不是猜的）；
3. 它自己没登记过——主动申请过就不重复。

### 报告回流是自动的

未读的报告在**下一轮开局自动注入**上下文（并标记已读），不指望模型记得去查
`read_diagnosis`。注入由循环做——模型不该有「假装读过」的机会。

### 完整回路实测

| 步骤 | 实际发生 |
|---|---|
| Agent 被卡住 | 4 步上限，两次自动验证都判定为环境问题 |
| 循环代它登记 | 请求 `20260912-134730-fb3f`，证据取自它的 trace |
| 特权侧验证 | 真去查了两条证据（icacls 报 Access is denied；换 basetemp 后 776 passed） |
| 写回签名报告 | `diagnose --report`，HMAC 签名 |
| 报告回流 | 下一轮 `consumed=True`，确实注入了开场上下文 |

**另一个值得记的对比**：同一批工具改好之后，「往 README 追加一节」这种窄任务
它做对了（内容准确，没有编造）；而之前那次「重写整个 README」它编了
「llama.cpp 需要 llama-cpp-python」。**任务越窄越具体，它编造的空间越小**——
这比「提示它不要编造」有用得多。

## 2026-09-12 · 额外可读根：读工作区之外，但不动工作区绑定

**起因**：想让它查一下 `D:\workSpace`（40 万文件、66 GB）并给清理建议。
第一版想法是「把工作区绑到那个目录」——被否掉了，理由很对：
**那是把「看一个目录」和「换个项目」混成一件事。** 工作区是身份，
记忆、索引、检查点都挂在它上面，不该被一个临时任务顺手换掉。

**改成显式授权**：`--allow-read <目录>`（可重复，来源是命令行 = 用户）。

| | |
|---|---|
| 读得到 | `read_file` / `list_dir` / `search_code` 认这份授权 |
| 写不到 | 写工具仍然锁在工作区内 |
| 不动的 | 工作区绑定、记忆会话、索引 |
| 粒度 | 逐目录，不是「开了一次就都能读」 |

越界时的报错会告诉人怎么授权，而不是干巴巴一句越界。提示词里也会列出
当前的可读范围，模型不必靠猜。

**真实验证**：不换工作区，授权读 `D:\workSpace` 之后，它自己列了顶层目录、
挑了 `game/` 列子项，并总结「那边是多个项目目录，game 看起来是游戏项目，
有源码、资源、文档和工具脚本」。全程没动工作区。

**顺带记一条**：它说「game 目录最大」是没根据的（它并没有量过大小）。
这类「听起来合理的顺口补充」是这个模型的一贯毛病，和前面那次编造
`llama-cpp-python` 同源。

### 补上测量工具之后

按「给工具，不给流程」的思路补了 `dir_stats`（通用，任何已授权路径可调），
**它立刻用上了**，而且产出了一份能看的报告：

| | |
|---|---|
| 量到的规模 | 483,835 个文件 / 67.0 GB（比我用 `Get-ChildItem` 数到的还多——权限受限的目录被静默跳过了） |
| 分类 | 能安全清理 ~30 GB / 需要你判断 ~15 GB / 不要动 |
| 依据 | 每条都带 `dir_stats` 的数字，并标注了不确定处（「venv 整体可能更大，但只确认了 torch 部分」） |

它甚至认出那批 2006 年的时间戳是 cargo 的占位，而不是真的老文件。

**这条对比很干净**：同一个模型、同一类任务，之前它「顺口编一个最大目录」，
现在它给出带数字的分类报告。差别不是模型换了，是**它手里有没有测量的工具**。
没有测量工具时，任何模型都只能猜。

### 过程中撞出的两个真缺陷

第一次跑这个任务时是**崩溃退出**的，服务端返回 400。补上服务端说明之后看清了：
`request (9772 tokens) exceeds the available context size (8192 tokens)`。

1. **预算建立在估算分词上，服务端用真实分词。** 中文/代码混排时偏差足以
   让本地判定放行、服务端拒绝。llama.cpp 本来就有 `/tokenize`，没理由不用——
   网关现在提供 `token_counter()`，装配时优先用真实的。
2. **那条拒绝是未捕获异常**，直接把整个运行打断。现在单独成类
   （`ContextOverflowError`），主循环接住并丢掉历史重发一次。
3. 附带一条：400 的报错原先只有一句「服务返回 400」，把唯一的线索扔了。
  现在带上服务端的说明——正是靠它才看清是超长，而不是格式或语法问题。

### 报告本身的两处数字错误，以及它牵出的设计问题

那份清理报告结构很好，但有两处数字和它自己量到的数据矛盾：

| 报告里写的 | 它自己的数据 |
|---|---|
| `tauri_player\src-tauri\target\` 约 8 GB | `src-tauri` 总共只有 5.1 GB——target 不可能比包含它的目录还大 |
| `pyvideotrans\.venv\` 约 1.2 GB | `.venv` 是 7.6 GB（1.2 GB 只是里面那个 `torch_cuda.dll`） |

两个误差方向相反，一个往上编、一个往下压，所以不是系统性偏差，是
**在数据上做加减时不严谨**。

这引出的是一个**新的失效模式**：前面几轮它的问题是「手里没数据所以编」，
这次工具把数据给足了，**结构也组织得很好**，但「从数据推出结论」这一步
仍然会错。所以「给它测量工具」解决了「无中生有」，没解决「有数算错」。

**结论：算术不该由模型做。** 数字只有两个合法来源——工具返回的、
程序算出来的。模型心算出来的数不算来源，不是因为它算不对，而是因为
**没有任何东西能核实它**。

已补：

- `calc` 工具（AST 白名单求值，不执行任意代码），回显算式与结果
  （`5.1 + 3.2 = 8.3`），引用时可追溯。
- 「写脚本再运行」这条路**本来就通**，实测写一个未落盘的脚本能跑出结果，
  真实磁盘不留东西——能力与隔离都在，缺的只是「想到用它」。

待定：

- **计算角色（子智能体）**：计算量大或复杂、或结果重要需要独立复算时派发，
  主循环只收结果。框架已有（角色 + 权限裁剪 + 派发闸门），加一个角色即可。
- **数字可追溯性检查**：交付物里出现的数字，逐条回到工具输出里找；
  找不到的标为「未经证实」。这是把「不能瞎编」从要求变成检查。

### 做完了，以及它的边界

**机制**：循环把每次工具调用的原始输出记进 `SourceLog`（模型改不了它——
它自己写进去的出处不算出处）；`check_numbers` 工具让模型自查草稿；
CLI 在交付时核对最终文本并标注，**只标注不阻断**。

**它能做什么**：挑出「在工具输出里根本没有出处」的数字——也就是心算出来的
合计、或者凭空写下的量。实测它能拦下这类。

**它不能做什么（这条更重要）**：它只查「这个数有没有出处」，**不查
「这个数是不是这个对象的」**。实测那两处错误里有一半属于后者——报告写
`target 约 8 GB`，而源里 8.4 GB 是 tauri_player 整体的数、5.1 GB 才是
`src-tauri` 的；8 与 8.4 只差 5%，够得着。这条边界写成了测试，
免得以后误以为它管得更宽。

**要拦住「配错对象」，得让工具的输出可解析**——有办法把「对象 → 数值」
的对应关系抽出来，才谈得上核对它有没有配错。这是下一步。

**过程中还修了一个误报**：`390.3 MB` 被报告写成 `0.4 GB`（正确的换算取整），
原先把单位排除在比较之外，就把它当成了编造。现在换算到同一量纲再比：
同一量纲 1% 容差，换过单位放宽到 10%（换算加取整本来就会挪几个百分点），
而真正的量级改动（5.1 GB 说成 8 GB，偏 57%）怎么放宽也拦得住。

### 配错对象也拦住了，以及噪声是怎么消掉的

**先看它第一次真实交付**：核对报了 25 处。其中大多数是报告里的**推算**——
「预估可释放约 7–8 GB」「通常占 Rust 项目体积的 80%+」。它们确实没有出处，
但那是模型该做的判断。混在一张单子里列，看的人会直接忽略整张单子——
**报出 25 处等于一处都没报**。

于是输出拆成三块：**配错对象** / **引用但无出处** / **推算**（只报数量，
不逐条列）。同时发现事件流那行（网页里看的就是它）把 35 个数字糊成一行，
网页还只显示「数字核对 → 失败」——一个**没有理由的红字**。补了 `note`
事件类型：系统说给用户听的一句话，工具那行只报成功失败。

**然后是判据本身。**「配错对象」要拦的正是上一节说拦不住的那类，做法是
让工具交出结构化事实（`Fact(对象, 值, 单位)`），核对时用**同一行里最近的
前置主语**判断这个数属于谁。第一次真实跑下来报了 **24 处**——几乎全是误报，
病因三个，都是实测才暴露的：

1. **主语的尾巴盖住了全名。** `.safetensors` 是
   `NoobAI-XL-v1.1.safetensors` 的尾巴，两者结束在同一处，按「位置最靠后」
   选中的是那个尾巴，于是比的是「所有 .safetensors 加起来」——每一处都对不上。
   改成**按结束位置取最近，位置打平取更长的那个**。
2. **数字里的点被当成了对象名。** `13.1 GB` 里的 `.1` 是个真实存在的扩展名，
   而且位置比真正的主语更靠后，必赢。要求主语**含字母**，并且**先定对象名，
   再看它有没有这一类的数**——「1 个文件」跟在文件名后面时，最近的对象是
   那个文件，而文件个数是目录的属性，那就不该拿来比（也不能退回去找更远的）。
3. **推算串进了配错检查。**「清了能省多少」不是「它有多大」。这一句里出现
   清 / 释放 / 删 / 省，这个数就跳过。

修完 **24 → 1**，剩下那条是真问题：报告把小文件 `torch_cuda.dll` 的 1.2 GB
写成了整个 `.venv` 的大小（实际 7.6 GB）——和上面那处旧账是同一类。

**存在性检查也在误报**，19 处：`dir_stats` 的渲染只列**前 8 个子项**，
而报告引用了第 9 个之后的东西，文本里自然找不到。结构化事实里有——
于是存在性检查也接受事实：出处分两处，工具渲染出来的文本，和它交出的
结构化事实。这一条把「不要动」那一节的整节误报清掉了。

**边界一（这条最要紧）：它的判断力取决于量过什么。** 复跑时模型只对工作区
根目录调了 `dir_stats`，报告里就有一句 `tauri_player\src-tauri\target\` 约 8 GB
逃过去了——不是判据不灵，是**没有任何东西能证明 8 是错的**：它手里只有
tauri_player 整体 8.4 GB。上一轮之所以能拦住，是因为那一轮模型自己也量了
`tauri_player` 子目录。所以：**讨论哪个子目录，就先量那个子目录。**

**边界二：事实按名字收，不带层级。** 报告在 `game-template-poject`（总量
925.9 MB）那一节写「.js 1.2 GB」，用的是全库 `.js` 的总和——名字对得上，
于是放行。要拦住这种跨层级的张冠李戴，事实得带上「它在哪个目录下」，
现在没有。

**这一轮的账**：真实任务 3 步 / 3 次调用（首次调用参数不合法，被工具拒绝后
自己改了重试）。交付物核对从 25 处噪声收敛到 **1 处真问题 + 4 处推算说明**。

## 2026-09-12 · 撞上步数上限不再等于失败（督导会话）

### 先说被否掉的那个方案

发现「撞上步数上限就停」之后只给了一句「任务未完成」，而检查点其实每一步
都写盘了、`--resume` 给的是**新增**预算——续跑这条路是通的，只是没人告诉用户。
我提的修法是**把这句话补上**。

被否了，而且否得对：那等于把系统的判断成本推给用户，还把一件事拆成两次对话，
第二次还得从头理解一遍。**明明放开步数就能解决的问题，不该让用户来分两次做。**

### 换成：预算用尽时由督导判断

「让它或者让一个新的监督者 AI 介入判断能不能自动加步数」——照着做。

督导是**一次结构化调用**，不是又一个子智能体：它不需要翻文件，需要的是判断。
给它的证据是目标、任务状态、最近发生了什么、机械统计；**不含主循环的推理
过程**——读到推理，它只会附和那个推理（和审查者必须独立是同一个理由）。
代价约等于主循环的一步，换回来的是一整轮预算。

| 触发 | 谁先反应 | 动作 |
|---|---|---|
| 同一个调用连续重复 | 机械层（提醒 → 不执行） | 参数一字不差时的第一道 |
| 重复升级到第 4 次 | 督导 | 续期 / 改道 / 收手 |
| 连续 8 步只有查看、没有产出 | 督导 | 同上 |
| 一轮预算用尽而任务未结束 | 督导 | 续期（默认），或说明为什么做不下去 |

两条线必须同时存在：督导会失败、也会看错，所以可检验的机械信号仍先挡一道；
而机械信号只看得到「参数相同」和「多久没产出」，看不出「它在换着花样绕」。
**总步数上限保留**，但它不再是任务预算，是一条安全线——没有它，一个卡住的
任务能把 GPU 烧一整夜。

### 实测：一次对话做完，而不是两次

**用的是一次注定撞上限的配置**（`--max-steps 1`，读一个文件说明它为什么不用
`eval`）。第一次调用后预算就用完了，此时督导被叫起来：

> 督导：续 1 步——Agent 已成功读取目标文件，获取了分析所需的全部代码信息，
> 但尚未输出最终结论。当前状态是信息已就绪，只差最后一步总结。

它只给 1 步（判断是「够走完剩下的事」），**任务在这一次对话里做完了**。
整轮 2 步 / 3 次调用（多出来的那次就是督导）。同一件事按老做法会以
「已达步数上限，任务未完成」结束，要用户再开一次对话。

**顺带量到一个好消息**：同一个任务用默认 `--max-steps 2` 跑（不需要督导介入），
是 2 步 / **2 次调用**——没撞上限时，一次多余的调用都没有。这个机制不常驻开销。

### 补掉的一个缺口

第一版的介入只认「参数一模一样的重复」。**换个花样绕抓不到**：每一步换一个
查询、永远不写，重复计数器每次都被重置——而实测那条 12 步的轨迹里换了 8 种
不同的调用，机械计数器一次都没响过。所以加了第二条升级线：连续 8 步只有查看、
没有产出，也叫督导。

### 没验证的部分

- **漫游那条线只有离线证据**（单元测试里 8 步换 8 个文件，督导在第 8 步被叫起来），
  还没有在真实任务里诱发过一次。
- **督导的判断质量没有量过**。27B 那次判断是准的（「信息已就绪，只差结论」），
  但只有一次；小模型当督导准不准，得靠回归集才看得出来。
- 回归集还没重跑。督导开着会改变「撞上限」那批题的归因，重跑之前不要
  拿它和旧数据比。

### 回归集重跑：50/50，而且督导一次都没被叫起来

按测量规程（重启服务让起点是冷的、整批跑）跑了 50 题：**50/50，平均 2.1 步**
（换 27B 时是 2.2 步），没有一道「自称完成但验收失败」。

两个发现：

1. **这一批里督导 0 次触发**。回归集是小题——平均 2.1 步，撞不到 12 步上限，
   也凑不满「连续 4 次重复」或「连续 8 步只看不写」。所以这批的结果与关掉
   督导等价，**不能算作对督导的验证**；它的验收在 `--max-steps 1` 那两次真任务里。
2. **平均输入 token 从 2763 涨到 3760**（+997）。查下来不是督导的账，而是
   这 26 个提交往提示词里加的东西：新增的五个工具（229 token）+ 四条工作流
   提示（246 token）= 475 token，**每个请求都要付一次**，×2.1 次调用 ≈ 998。
   数字对得上，细节记在 `benchmarking.md`。

第 2 条比第 1 条重要：它说明**每加一个能力，都在给每个请求加税**。
现在系统提示里工具清单占 521 token，而正文只有 143。

## 2026-09-12 · 工具改成「索引 + 按需展开」

把那笔税收回来。做法是用户提的那两条：**分类** + **`tool_help` 按需查**，
相当于把索引树那套「逐级加载、找到就停」搬到工具层。

### 量出来的账

| | token |
|---|---|
| 十五个工具的整份说明（旧） | 665 / 请求 |
| 索引：名字 + 参数名 + 一句干什么，按类分组（新） | 210 / 请求 |

**每个请求都要重述一遍**，所以这不是一次性开销。同一批 50 道题里真正用到的
只有 6 个工具——没被用到的那些，每一轮都在收费。

### 两处不能省

- **参数名必须留在索引里。** 语法约束给的是「所有工具参数的并集」，它不说
  哪个参数属于哪个工具；模型在写下调用之前，参数表只有这一处可见。实测它
  会把一个工具的参数搬到另一个工具上。
- **「什么时候用」不能跟着一起收。** 那部分本来就在常驻的「工作方式」里
  （先量再判断、不要心算、跑测试优先只跑相关文件、缺依赖用 `uv add`……），
  收掉工具描述不等于收掉指引。核过一遍，`run_command` 的要点全在常驻那节。

有一条我特意从按需层挪回了常驻：**`run_command` 是在「未落盘改动的试跑副本」
上跑的**。不知道这点，它会把真实失败当成预先存在的噪声放过——而这类错误
回归集抓不到（那批题都是一次改对）。所以处理原则是：**收的是「怎么用」，
留的是「会改变结论的事实」**。

### 结果

同一批 50 题，冷启动服务后整批跑：

| | 通过 | 平均步数 | 平均输入 | 总耗时 |
|---|---|---|---|---|
| 整份说明 | 50/50 | 2.14 | 3760 | 560s |
| 索引 + 按需 | 50/50 | 2.06 | **2868** | 430s |

**通过率没掉，输入 token −24%。** 耗时也降了，但那个受机器状态影响，不当结论。

真正的收益在下一次：现在多一个工具的成本是「索引里一行 × 每个请求」，
而不是「整段说明 × 每个请求」——工具集扩张不再是线性的税。

## 2026-09-12 · 把 50 题交给一条会话

### 先回答那个问题

回归集是**一题一个会话**，而且比那更彻底：一题一个临时工作区、一题一个
新建的循环（新索引、新上下文）。这么设计是为了可比——一道失败不污染下一道。

代价是**它从来没量过长任务那条轴**。所以加了第二条仪器：
`bench --together` 把 50 题铺进一个工作区（每题一个目录，里面有 TASK.md、
起始代码、验收测试），**不给题目清单**，只告诉它题在那儿，让它自己去读、
自己排、自己验、自己收尾。

### 结果：9/50，而且收尾是督导决定的

| | 数值 |
|---|---|
| 验收通过 | **9/50**（01–09 全对，后面 41 道没开始） |
| 一条会话 | 62 步 / 66 次调用 / 167338 输入 token / 705s |

它确实是自己在干活：读 TASK.md、列目录、改代码、跑测试，一路做到第 9 道。
**上下文重置 0 次**——历史有上限，提示词稳定在 2.5–3K，没撞过预算线。

**督导被叫了 4 次，四次判断都立得住**（这是它第一次真正面对长任务）：

| 步 | 判断 | 理由 |
|---|---|---|
| 12 | 续 10 步 | 进展正常，没陷入循环 |
| 22 | 续 20 步 | 已完成 5 道，总上限还剩 98 步 |
| 42 | 续 20 步 | 已解决前 7 道，剩 78 步够用 |
| 62 | **建议收手** | 连续多步无产出 + 两步因输出截断解析失败 |

按老做法，这条会话在第 12 步就结束了，用户要自己再跑五次。

**它自己的收尾报告是错的**，而且是**往悲观的方向错**：它说「已完成 7 道
（03–09），尚未跑验收确认」，实际是 9 道通过（含 01、02）。两种偏差都真实
存在——所以判定只能看验收命令的退出码，不能看它说什么。

### 暴露的三个问题（都不是「模型不会做」）

**一、命令形状错误被报成了权限问题（已修）。** 卡死的直接原因在这里：
它把 `python -m pytest 09_split_function/test_acceptance.py -q` 当成**一个**
字符串放进 `command` 数组（应该拆成五个元素）。白名单于是把它当成一个叫
「python -m pytest …」的程序，回了一句「不在白名单内，需要用户批准」——
**理由指错了方向**。它据此去申请权限，而无人值守时没人可问，于是连撞三步，
转而决定自己写个批量跑测试的脚本，最后撞上输出预算收尾。

现在这种形状错误直接说形状，并给出正确写法。

**二、自动验证在「一个工作区里有很多件事」时给出的反馈是误导的。**
`detect_test_command` 只要在根目录下发现任意 `test_*.py` 就返回「跑全部测试」，
于是在这个铺盘里，每改完一道题都跑 50 个验收、报「失败」（另外 41 道还没做）。
反馈与它刚做的改动无关——它只能自己想办法绕开。
一题一工作区时这是对的；「把这一批都修了」这种任务里它是噪声。
这次只加了信息（说清跑的是哪条命令），判据没动——**收窄到「只跑相关测试」
需要先想清楚怎么从改动映射到测试文件**，那是下一件事。

**三、输出预算仍然是硬的。** 三次解析失败里，两次是「内容疑似被输出预算截断」
（输出预留 1228 token，写不下一个稍大的文件）。翻倍重试救回过一次，
写那个批量脚本的两次没救回来——**督导的收手理由正是这个**。这条早先记在
「动态配额」的缺口里，现在它有真实代价了。

### 还有一条：派发压根不可达

这条仪器想量「任务派发」，但**会话内部没有派发的入口**——派发是运行级模式
（`--delegate` 在启动前决定，判断一次够不够）。会话里没有「把这块交给
子智能体」这个工具，所以主循环想要派活也无从派起。

这跟你最初的设计（主循环分派、子智能体实施、审查独立）之间还差一步：
**派发要能在会话进行中被调用**，而不是启动前定一次。这条没做之前，
「大任务交给子智能体」实际是不成立的。

## 2026-09-12 · 会话内的派发（补上那一环）与输出预算

### 输出预留：是比例写死，不是数写死

先回答两个问题，都有代码依据：

| 问题 | 答案 |
|---|---|
| 输出预留写死了吗 | 比例写死：`OUTPUT_RESERVE_RATIO = 0.15`，额度 = 窗口 × 0.15（8K 就是 1228），**每个请求**都以它作 `max_tokens` |
| token 上限去掉了没 | 没有，而且只翻倍一次：被截断后 `chat_with_escalation` 翻倍重试（2 次封顶，最多 2456） |

真正的毛病不在数字，在**被截断时给它的反馈**：原来是「请只输出规定的 JSON」——
那是在纠形状，而这一轮的毛病是一次说得太多。它照做重来一遍，还是那么多，
于是同样被截断（上一次长任务里连撞两次，督导据此收手）。

现在分两步：截断会被单独标成一类（`kind="truncated"`），循环据此
**把这次任务的输出预算抬到 30%**（记在这次任务里，不再每轮撞一次），
同时告诉它**把这一轮拆小**——只改一处、或先交一部分，剩下的下一轮接着做。
抬高是封顶的：抬的是输出的钱，付的是输入的预算（8K 窗口下 30% 是 2457，
留给上下文装配的只剩 5735）。

### 会话内的派发入口

`dispatch(goal, acceptance, targets, constraints, out_of_scope)` 进了会话：
主循环可以自己决定把哪一块交给子智能体——独立上下文实现、另一个独立上下文
审查，只把结论收回来。

几条刻意的设计：

- **闸门照旧**：没有验收标准不许派。没有可执行的判断依据，实现者做到什么
  程度都算完成，审查也会退化成互相附和。
- **同一份 diff**：子智能体的写工具绑的是主循环那一份 `PendingChanges`，
  所以两份改动汇成一份，用户只确认一次，也不会出现两套矛盾的视图。
- **不递归**：子智能体的角色工具表里没有 `dispatch`。
- **失败不外溢**：派发那边炸了，主循环收到一条失败结果继续干活。

### 真实的账：一次派发值多少

真任务（修 `sum_to` 的差一错误）实测：主循环 **2 步**，
派发时**第一步就发出去了**，实现者改对、审查者判通过、改动落盘。

但这里抓到一个**记账漏洞**：用量报告说「2 次调用 / 3189+287 token」——
子智能体那一路（实现、审查、判定）**一次都没进表**。那张表是调这块时
唯一的账本，漏掉主循环之外的全部开销，报出来的就不是「这次任务花了多少」。

修法是把网关包一层来数，四处调用一处不漏；工具把这段开销作为 `Usage`
报回循环。同一件事重跑：

| | 修之前报的 | 真实 |
|---|---|---|
| 调用次数 | 2 | **10** |
| 输入 token | 3189 | **12223** |

这组数字本身也是结论：**一次派发的成本约等于主循环十步**。所以「什么时候
值得派」是个真问题，不是修辞——小题派发是亏的，这也正是那条常驻提示
（一句话，24 token，完整取舍放进 `tool_help`）要说的。

### 引导「按批派发」：写进提示词没用，但长任务里抓到了别的东西

用户提出：单道题不值得派，但**一批题一起派**是划算的——固定的那几次调用
被摊薄，而长任务里稀缺的本来就是主循环的步数与上下文。这个判断对，所以把
引导写进了两处（常驻工作方式 + `dispatch` 的描述），并把实验目标里
「一道一道做」那句删掉——它和批派发是矛盾的。

**结果：三次长任务实验里 `dispatch` 一次都没被调用。** 规则写进提示词，
不等于模型会用它。

但这三轮跑出了更值钱的东西。第三次实测：**72 步 / 10 道通过**，而状态里
显示它碰了 49 道题——去看它到底写了什么：

| 题 | 任务要求 | 它做的 |
|---|---|---|
| `13_case_insensitive` | 改 `search.py` 的 `contains` | **新建 `match.py`**，写了一版看着对的 `match(s, target)`；目标文件一字未动 |
| `49_strip_prefix` | 改 `prefix.py` 的 `without_prefix` | **新建 `strip_prefix.py`**，函数写得完全正确；目标文件一字未动 |
| `50_retry_count` | 修 `retry.py` 的 `attempts` | 重写了目标文件，但**把函数名改成了 `retry_count`**；测试 `from retry import attempts` 直接 ImportError |

**这是赶工，不是不会做。** 一步里并行写一批文件，内容是按 TASK.md 那段
散文**猜**出来的——散文说的是意图（「改成不区分大小写」），不是代码现状。
于是产出一堆看着像对的、却对不上的东西：名字像、位置错、或者函数名被
「顺手改得更合理」。

这也解释了为什么同一批题在**一题一会话**里是 50/50，在一条会话里是 10/50：
差别不在模型能力，在**没有「先读再改」这一步**。单题模式里上下文小、
一次只干一件事，读一下文件是自然的；50 道的积压之下，读文件看起来像浪费。

顺带修掉一个真会让长任务崩掉的缺陷：`LlamaCppGateway` 的客户端超时是**死的
180 秒**，而输出预算抬高后一次生成可能更长——两次实验里有一次就是这么崩的
（`ReadTimeout` 直接终结整条会话，检查点还在但那一轮全丢）。现在每请求的
超时按 `max_tokens` 放大，而且超时与「连不上」分开报：原来那句「请确认服务
已启动」把排查方向指错了——服务好好的，只是这次生成太长。

### 让验证跟着改动走（这一刀是对的，但这一轮没跑完）

改了两处，都是机制而不是提示词：

1. **自动验证的范围跟着改动走**。原先在工作区根上跑整条测试命令——多任务
   铺盘里就变成「改一道、报另外 41 道的失败」。现在从被改文件所在目录往上
   找，最近的、自己就带测试的那一层就是验证范围；一次改多处就逐处验、
   逐处报（「改了 8 处：5 处通过、3 处没过，没过的：13_…、49_…」）。
2. **督导承担行动建议**。它的话直接发给主循环，而且只在被叫起来时付费——
   正是放「积压时按批交给 dispatch」这条建议的地方。

第四次长任务跑到约第 80 步时我把它停了（约 40 分钟）。**停的原因本身是个
发现**：它比上一次慢了一倍多（72 步 / 16 分钟 → 80 步 / 40 分钟）。
当时我把原因归到「带范围的验证每步起好几个 pytest」——**这个归因站不住**：
这一轮它**派发了两次**，每次十来个调用，那才是大头。

而且我提的那个优化（把多个范围合成**一次** pytest 调用传参）**做不了**，
实测过两种写法：默认模式下那 50 个目录的测试文件**同名**（都叫
`test_acceptance.py`），同一进程里收集会报 import file mismatch；
换 `--import-mode=importlib` 能解决同名，但同目录的 `from search import ...`
又失配，两个都 ERROR。所以省时只能从别处来——**跑前 N 道**：
题集顺序是稳定的，前 N 道的结果可以和整批跑的前 N 道直接比。

停下前看到的两件事：

- **它真的派发了**（两次）。检查点里一度躺着子智能体的状态，goal 是
  「查看 50 道题每道题的 TASK.md 与代码，判断哪些做完」——是督导那条
  建议的形状。
- 那次派发**失败了**，而且失败得很有意思：实现者撞上「连续 10 次重复调用
  `write_file`」的保护，收手时留下的话是这个原因。

### 派发这条链路上又被揪出两个缺陷（已修）

**一、审查者的证据包没有范围。** `run_delegated` 给审查者准备证据时调的是
无参数的验证，于是退回根目录跑整条命令——在多任务工作区里，审查者收到的
是一屏 **50 个 ERROR**，它据此写下的结论自然没有意义。现在无参数时会退回
「这次会话改动过的全部文件」来推导范围。

**二、子智能体会覆盖主循环的检查点。** 主循环和子智能体跑在同一个工作区、
共用同一个 `task.json`——派发一次，主循环的进度就被子智能体的状态替换了。
崩溃或续跑时读到的会是别人的进度。现在子角色用自己的 `task_id`。

### 子智能体有权说「太大」（用户提的）

用户指出：**派活之前该先规划**，而「过大任务」或者「不合理的行动」，
子智能体应当能先反馈「这块我独立做不完，需要拆解」。

这条正好对上那一轮的失败：实现者拿到超出预算的批量任务，硬做到撞上
重复保护，回来的信号是「连续 10 次重复调用 write_file」——**一句主循环
无从行动的话**，然后它还被送去审查（审的是个半成品）。所以做了两处：

| 位置 | 做法 |
|---|---|
| 派之前 | `dispatch` 带超过 10 件时**当场拦下**，并说明算法：子智能体一轮 20 步、一件活 2～3 步 |
| 角色提示词 | 实现者与审查者**开工前先估规模**；估出做不完就直接 `done=true`，final 以 `【太大】` 开头，写清原因和一种可行的拆法 |
| 送回主循环 | 「太大」和「做砸了」分开报：前者让它拆小再派，后者让它改代码 |
| 送审 | 说了「太大」、或者撞了步数上限（没 finished），都**不送审**——审半成品只会把「任务太大」误报成「实现不合格」，再触发一轮注定失败的修复重派 |

步数预算写进了角色提示词（`{limit}` 换成这一轮真实拿到的步数）：不写数字，
它会拿主循环的预算来估自己的活。

### 把那条仪器跑到能信：20/20

前面那次的读数一直不好看，逐个查下来，**大半是仪器自己的毛病**：

| 现象 | 真因 | 改法 |
|---|---|---|
| 6 步就收工、只做 5 道 | 目标里写着「做到你确实做完的那一批为止」——**等于给了它一个体面的退出理由**，而它照字面执行 | 改成「尽量多做：除非预算耗尽或确实卡住，否则不要停」 |
| 自动验证通过后立刻收尾 | 循环那句「没有别的要改就直接收尾」——它只知道**这次改的地方**通过了 | 改成「这只说明这次改的地方通过了；任务整体做完没有由你判断」 |
| 连撞 18 次 pytest 全失败 | 它写 `cd` 换目录、又用 `cwd: /workspace`（绝对路径）。两个报错都准确，但都没说**正确写法** | 报错里直接给写法：换目录用 `cwd`（相对工作区）；路径越界时说明要写相对路径 |
| 20 步耗在「修」import file mismatch | 50 个目录里的测试文件**同名**，根目录跑 pytest 必冲突——布局的坑，不是题目的难点 | 铺盘时把验收测试改成工作区内唯一名 |

改完之后：**20/20**（60 步 / 64 次调用 / 205K 输入 / 17.8 分钟）。
对照整批跑的前 20 道是 9～10 道。**这不是受控实验**——几行之间同时变了好几
样东西；它证明的是「当前这一版能做到」，不是「哪一项值几分」。

顺带又是一个关于「自述不可信」的证据，方向却相反：收手时它报「未完成
01-08、11-14、16-20 共 17 题」，而客观验收是 **20/20**。它把大部分已经写对
的题忘了——状态块里的 `done` 只留最近 8 条。**长任务里「我做到哪儿了」
需要一个不会被挤掉的载体**，这是下一步该做的东西。

### 状态块：8 条太少，但不能靠调大数字

先量了那笔账（同一个块**每轮都注入**，所以每条都是每个请求的税）：

| 做法 | 8 项 | 20 项 | 50 项 |
|---|---|---|---|
| 只把上限调大（全部列出） | 84 | 203 | **503** token/请求 |
| 改成「列最近 8 + 总数 + 指针」 | 88 | 115 | **115（恒定）** |

所以改法和工具清单一样：**完整记录留在外面，块里只放摘要 + 指针**。

- `state.done` 不再截断（它本来就落在检查点文件上，不花提示词的钱）；
- 块里写「已完成 20 项（只列最近 8 项）…」+「完整清单: .agent/progress.md」；
- 循环每记一条就把全量渲染到 `.agent/progress.md`，模型需要细节时自己读。

另外两块值得记在心上：

- **每步之后跑的不是审查，是自动验证**（跑测试，只在有改动时）；审查者只
  存在于派发路径。所以「把状态维护交给审查者」这件事要先问它解决哪个问题
  ——而我们手上那条证据指向的是**机械记录的截断**，不是模型自填的
  `current` / `hypothesis` 不准。
- 真要交出去，也不该**每步**一次：一次额外调用是实打实的成本，而状态
  失真集中在几个时刻——上下文重置前后、状态要溢出时、派发前后、督导介入时。
  那几处触发一次「整理会话」是合理的设计，但要先量它有没有用。

### 「每轮先收集信息、规划再行动」：规划不必每轮，但**规划前必须看一眼**

用户问的方向是对的，实测把边界画清楚了：

| 问题 | 实测 |
|---|---|
| 每轮先收集信息？ | **不必。** 那批 50/50 的单题里，52 次写入中有 **48 次**发生在「整个任务一次 `read_file` 都没发生」的情况下——它靠题目描述 + 整份重写就把小题做对了。每轮加一次信息收集 ≈ 每步多一次调用，而单题平均只有 2.1 步 |
| 规划前先收集？ | **必须。** 见下 |
| 规划本身要有吗？ | **已经有**（运行级 `decompose`、每轮 `thought`、派发前 `TaskSpec` 闸门），只是长任务那条仪器没用过它 |

**规划不看环境的实测形状**：`decompose` 一次调用产出 20 步，每步都有验收
标准、都有范围——形状完美——而范围写的是 `task_1/`…`task_20/`，真实目录是
`01_off_by_one`…。**那些目录根本不存在**，于是每一步的范围闸门都会把改动
挡在外面，整份计划等于没有。模板里明明有「已有信息：{context}」，调用方
一个字没传。现在拆解前先看一眼工作区（目录条目 + 检索到的相关片段）。

顺带又修了一个「纸面能力」：**`--autonomous` 这条路从来没跑通过**——
`plan.py` 里用了 `Config` 却没导入，一执行就 `NameError`。所以「先规划再
行动」在这之前只是文档里的东西。

**修完之后两条路都到 20/20，账几乎一样：**

| 配置 | 通过 | 步数 | 调用 | 输入 token |
|---|---|---|---|---|
| 一条会话自己安排 | 20/20 | 60 | 64 | 204944 |
| 先拆解、再逐步执行 | **20/20** | 82 | 82 | 200964 |

差别不在总量，在**形状**：逐步执行那条每步是独立上下文（提示词更小、
不被前面的细节污染），代价是每步要重新侦察一次，所以步数更多。
它真正的价值是**把记忆外置到计划文件上**——计划落盘、不怕上下文重置、
也不会像状态块那样被挤掉。

结论：**「先收集信息」要绑在需要它的那个动作上，而不是做成每轮的一个阶段**
——拆解前看工作区、改已存在的文件前看接口（长任务里那句「先读验收测试」
就是这个，它把前 20 道从 9～10 提到 20/20）、派发前写清验收标准。

### 「按步注入」把子智能体的角色抢走了（用户指出）

用户看到计划是「按步注入」之后问了一句：这是不是不太对？**验证下来他是对的。**

| 事实 | 证据 |
|---|---|
| 每一步**就是一份派发契约** | `PlanStep` 的字段是 `goal / acceptance / scope / status`——和 `TaskSpec` 同形 |
| 但拆解时**没问「谁来做」** | `DECOMPOSE` 要求能一次做完、有验收标准、声明 scope、顺序、数量——就是没问执行者 |
| 执行由 harness 直接跑 | `execute_step` → `loop.run(render_step_prompt(plan, step))`，没有派发分支 |
| 后果：子智能体从未登场 | 那条路上 `dispatch` 用了 **0 次**；验收只剩「跑测试」这一种机械判断 |

也就是说，它**不是**少了什么功能，而是悄悄换掉了两样东西：派发的决定权
（harness 在拆解时替所有步骤决定「都自己做」），以及**独立审查**——
测试能说「过没过」，说不出「这处改得是不是偷懒了」。

改法照用户的直觉：**把「谁来做」纳入拆解**。

- `PlanStep` 加 `executor`（`self` / `subagent`，缺省 `self`——派发要付固定
  成本，不该由缺省打开）；
- 拆解提示词要求逐步声明执行者并给出判据（一次改一处自己做更快；要读很多
  文件、验收标准清楚的交给子智能体）；
- 执行时分支：`subagent` 的步骤用这一步的 goal/acceptance/scope 组成
  `TaskSpec`，走实现者 + 独立审查者，**成不成由审查结论定**（不是由
  「测试过了」定），改动仍落在同一份待确认里。

冒烟实测（手写一份 `executor: subagent` 的单步计划）：实现者改对、审查者
自己跑了一遍并给出三条具体依据、判定通过、步骤标成 `done`、改动落盘。
代价也量到了：**这一步 11 次调用**，而自己做那一步约 4 次——固定成本
确实是十来次调用，所以「什么时候值得派」仍然是拆解那一步要判断的事。

**还没量的**：20 道小题的拆解里，模型会不会正确地把所有步骤都判成 `self`
（按判据它应该这么判）；以及独立审查到底抓到过什么（要统计审查结论非空的
比例，得跑一批有真实缺点的任务）。

### 给「值不值得派」补上反馈回路

主循环对子智能体的认知原本是**静态的两句话**（工具清单里一行 + 常驻判据一条）。
它不知道在这个工作区里派出去是赚是亏——而教训机制记的是**任务级**成败，
不是派发级的，所以一次派发失败不会回流到下次判断。

补法：每次派发结束记一笔战绩（`<工作区>/.agent/dispatch-log.md`），
并且**只在两个「正好要判断」的时刻取用**——模型问 `tool_help("dispatch")`
时（那正是它准备派的时刻）、拆解前收集环境时（那正是它决定「谁来做」的时刻）。
常驻提示词里一个字都不放：那是每个请求的税。

记账内容：时间 / 结果（通过 / 未通过 / 没结论 / 太大 / 失败）/ 几次调用 /
几轮 / 目标几件，外加一行理由。战绩在**装定时**读进工具说明（跨运行生效；
同一次运行内它刚亲眼看过结果，不需要刷新）。

**端到端测试当场抓到一个缺陷**：派发有**两条路**（会话内的 `dispatch` 工具、
计划里 `executor=subagent` 的步骤），而记账先写在工具那一层，于是计划那条路
跑完一步，日志文件根本没生成。移到共用的 `run_delegated` 里才两条都覆盖到。
——这就是为什么「离线单测过了」不等于「链路通了」。

实测（手写单步计划 + 真实模型）：

```
- 09-12 23:22 [通过] 9 次调用 / 1 轮 / 目标 1 件 — 审查结论明确给出了验收标准满足的依据：…
```

下一次装配时 `tool_help("dispatch")` 会带上：「本工作区记过的派发（共 1 次：
通过 1 次）。最近几次：…」

### 对照实验：一次真实的批量派发，78 次调用

问题：战绩会不会**改变它下一次的判断**？第一轮先制造一次真实的批量派发
（明确要求「把这 8 道一起交给子智能体」），第二轮再给同样形状的任务，
看它开头怎么决定。

**第一轮的账（真实模型、8 道题）**：

```
- 09-12 23:44 [没结论] 78 次调用 / 2 轮 / 目标未声明 — 审查没有得出结论…
```

客观验收：**8/8 全部通过**。所以这一轮的真实故事是：**活干成了，但审查没能
给出结论**（第二轮审查没跑完，`inconclusive`）。

三个数值得单独记：

1. **78 次调用做 8 道题 ≈ 9.75 次/题**——和单题派发的成本几乎一样。
   也就是**批量并没有摊薄多少**：摊薄的只是「派发 + 判定」那几次固定开销，
   实现者自己仍要一题一题做。这一点修正了我之前的判断（我说过「一批摊薄
   固定成本之后才划算」——对，但摊薄的量很小）。
2. **审查者的失败被记成了错因**：「审查者自己撞上了步数上限（8 步）」，
   而它的步数上限是 20 步，真实原因是督导判断该收手了。现在那半句改成
   引用审查者自己的话，不再替它猜。
3. 「目标 0 件」是模型没声明 targets；现在写「目标未声明」，不再用一个
   会被误读成「零个目标」的数字。

**第二轮我没让它跑完**：它在第一步里生成超过四分钟还没动作（GPU 满载），
而这个补充观察的价值不足以再等十几分钟。所以「战绩会不会改变判断」这件事
**仍然没有答案**——日志只证明了「看得见」，没证明「会用」。按这个项目里
反复出现的规律（引导写进提示词 ≠ 模型会用），这一条不该想当然。

### 把「批次大小」做成可检验的约束

上一轮那句「一次交 3～5 件」只写在工具描述里——而描述已经反复证明是软的。
现在分三层，各管一件事：

| 层 | 做什么 | 为什么在这一层 |
|---|---|---|
| schema 必填 | `targets` 必填 | 件数是所有跟批次大小有关的约束的**前提**：实测那次 8 件的派发没声明目标，于是「别超过 5 件」根本落不了地，日志里只剩「目标未声明」 |
| 结果里告警 | 5 件以上：明说「审查者容易给不出结论」，并给实测依据 | 那一刻是它决定**下一批派多少**的唯一时机 |
| 硬拦 | 10 件以上直接拒 | 那是「做不完」的量级（实现者烧光预算、交回半成品） |

常驻那句也补了「一次别超过 5 件」——因为上一轮的教训是：**描述是软的，
常驻判据才 shape 行为**（`survey` 就是补了常驻那句之后才从 0 次变成用起来的）。

**这条还没在真实运行里验证过**：单测覆盖了三层，但要看到它真的因此把 8 件
拆成 5 件，得再跑一次带派发的真实任务。

### 用户提的一条原则：别把能力标定写死

原话：**不希望 Agent 内存在太多写死的数量上限和规定**——外部供应商的 API
调用能力显然比本地大模型强，那些限制反而会降低效率、影响它发挥。

于是把 65 个模块级数字常量盘了一遍，分成三类：

| 类别 | 例子 | 该不该随能力变 |
|---|---|---|
| 安全边界 | 命令超时上限 600s、dir_stats 条数安全网、永久禁止清单 | **不该**——它防的是不可逆后果 |
| **能力标定** | 步数上限与倍数、批大小 5/10、`DONE_INLINE 8`、预算比例、预取 400/1000、截断 600、重复检测 2/3/4 | **该变**——而且只会因为模型更强而被突破 |
| 机械常数 | 网络超时、keepalive、日志条数 | 无关 |

判据写进了设计文档 §2.7：**这个数字只会因为模型更强而被突破吗？** 是 → 可调
且默认不该压低；防的是不可逆后果 → 写死。

已经动手的两处：

1. **上下文窗口不再被我们砍**。原先 `MAX_AUTO_WINDOW = 32768`，注释写着
   「保留设计前提」——那是为了验证我们自己的设计。远程供应商报 200K 时我们
   按 32K 跑，能力被自己砍掉五分之四。现在探测值直接采用，想限制就显式给
   `--window`；代价（预算比例会放大 → 每个请求装的更多）在用量报表里看得见。
2. **批大小的两个数从工具里搬进配置**（`Config.max_targets` / `review_limit`
   + `--max-targets` / `--review-limit`）。它们是按本机 27B + 20 步预算实测
   出来的，不该替强模型做决定——远端模型一次带 20 件完全可能更划算。

**没做完的部分**（记下来免得忘）：还有五十来个常量散在各模块里，其中相当
一部分（预取 400/1000、截断 600、`DONE_INLINE 8`、重复检测 2/3/4、预算比例）
同属「能力标定」。它们现在的样子是：**能改，但要改代码**。往下的做法是逐步
收进配置，并让每一项都能说出「它从哪来、被谁覆盖」——因为一条看不见来源的
限制，和一条写死的限制一样难用。

### 把「能力标定」做成一张可查、可改的表

接着上面那一步做完了骨架：`agent_dev/limits.py` 是登记表，`agents-dev limits`
是入口。

```
$ agents-dev limits
       值  来源     能不能改     名字
       3  默认     可覆盖      repeat_block_at
          重复到几次不再执行：第三次中间没有任何别的动作，结果不可能变
       1  默认     写死        path_confinement
          写操作不出工作区（不可覆盖）
```

- **来源要看得见**：`默认` / `配置`（工作区 `.agent/limits.json` 覆盖过）——
  一条看不见来源的限制，用起来和写死的限制一样难受：你不知道该不该动它。
- **不改代码就能动**：`limits --set repeat_block_at=5`；安全边界（path_confinement、
  永久禁止清单、超时上限）标成 `写死`，给了值也会被拒，理由明说。
- **一套默认，一处出处**：循环里的重复检测/空回合/漫游/步数倍数、派发批大小、
  survey 预算、输出预留比例都从登记表取值；模块级常量保留名字（外部按此导入）
  但值来自登记表，不再各写一份。

实测覆盖是否真的生效，而不是只打印好看：把 `repeat_block_at` 从 3 改成 10，
同一个文件连读两次都真的执行了（默认下一次就提醒、第三次不执行）。

**还剩什么**：预取 400/1000、截断 4000/600、`MAX_INDEX_FILES 2000`、
`INDEX_SECONDS 20`、预算比例那一组还散在各自模块里——它们同属能力标定，
现在的样子是「能改，但要改代码」。骨架已经在了，往下是逐个搬进来。

### 第二批搬迁：影响最大的那些先搬

搬完了这几组（都能说出「现在是多少、从哪来」）：

| 搬了什么 | 为什么它值这个优先级 |
|---|---|
| 预算比例一整组（软/硬触发线、热记忆/状态/代码/检索/教训配额、固定配额封顶、小窗口模式阈值） | 它决定**每次请求能装多少上下文**——强模型上这套比例的意义完全不同 |
| 索引上限（`max_index_files`、`index_seconds`） | 决定「这个仓库到底建不建索引」；本机 27B 上 2000 文件附近的平衡点，换机器就变 |
| 工具输出截断（`max_output_chars`） | 硬截断会把「失败在哪」直接切掉——强模型读得下更多 |
| 开局预取（符号表 400 / 代码片段 1000） | 每次运行都要付，且与模型强弱强相关 |

**一条判据顺带理清了「哪些不用搬」**：工具的**参数默认值**（`search_code` 的
`max_results`、`dir_stats` 的 `top`/`seconds`、`survey` 的 `budget`）本来就
**每次调用都能覆盖**——模型想要更多，自己在参数里给就是了。真正需要搬进
登记表的是**模型改不动的那些**：循环内部的阈值、harness 侧的开销、工具的回灌上限。

### 那个偶发测试：没查到根因，但让它会自己说明

`tests/test_diagnosis.py::test_签名报告才算数` 偶发失败过两次（同一条测试、
不同时间）。这次认真查了：单跑 20 次全过；带诊断跑全量三次也全过——**没复现**。

它守的是签名边界（「报告只应由具备真实环境权限的一侧出具」），留成「偶尔红」
比红更糟。所以这一轮的处理是：**把判断依据写进失败消息**——密钥文件在不在、
多长、文件里存下来的签名、用当前密钥重算的结果、请求数。下次再红，一眼能看出
是密钥被换、签名不匹配、还是读到了别的请求。

根因没找到这件事要留着：**未知的偶发不会因为没复现而消失。**

### 那个偶发：根因找到了，是生产代码的 bug

后面它又红了几次（换了一条测试红——同一个文件里凡是要验签的都会红）。这一轮
终于抓到了，而且**根因在 `diagnosis.py`，不在测试里**：

```
密钥文件 存在=True 长度=31        ← 密钥是 32 字节，strip 吃掉了一个空白字节
存下来的签名=1693d099…   用当前密钥重算=f9297672…   ← 两次用的不是同一把钥匙
```

`ensure_key()` 写回 32 字节随机串之后，**返回的是原样**；而读取走 `load_key()`
——**会 `.strip()`**。于是只要随机密钥的首字节或末字节恰好落在空白上
（约 **4.6%**），就会出现「签的时候一把钥匙、验的时候另一把」：
签名永远对不上，而两侧都不报错。表现为偶发失败，查起来极难。

**这不止是测试的事**：生产里同样发作——特权侧新生成的密钥签出的报告，
读的一侧验不过（约 5% 的装机概率），而报错只说「来源无法验证」。

修法：密钥改用 hex 生成（纯 ASCII、不含空白，`strip` 幂等）；老格式仍读得出来
（两条路径都 strip）。测试钉住的方式很重要——**第一条测试没钉住它**（走的是
「文件已存在」的分支，旧实现也会过），必须把随机源钉成「首尾带空白」才逼得出来。

这件事的账要记两笔：

1. **「偶尔红」不能留**。它守的是签名边界，红了没人当真；而它背后是 4.6% 概率的
   真 bug。
2. **诊断信息要写进失败里**。第一次红我加了自说明，第二次红（诊断代码自己有个
   `os` 没导入的 bug）反而更有信息量——它证明了「诊断跑了 = 偶发复现了」。

### 批次验证做完了：上限该拦的不是「做不完」，是「审不完」

第三次复跑（给足 8 步预算、把 8 道题的起始代码复原、`.agent/` 里的战绩保留）：

```
- 09-13 08:43 [没结论] 11 次调用 / 1 轮 / 目标 9 件 — …
```

| 观察 | 结果 |
|---|---|
| 读到战绩后会不会拆小 | **不会**：它声明了 **9 件**（8 道题 + 一个目录），比上一轮的 8 还多 |
| 活干得怎么样 | **8/8 客观通过**，只花 **11 次调用**（第一次同类派发是 78 次） |
| 审查那一步 | **第三次「没结论」**——三次批量派发的审查全没给出结论，其中两次活是做对的 |

所以三层约束里**只有「targets 必填」真正生效**（它这次声明了件数；上一轮是
「目标未声明」）。告警那层没用，因为告警在**事后**，而它下一次照样派 9 件。

顺着这条证据把上限改成**硬拦**，而且理由换了——原来我以为是「实现者做不完」
（子智能体步数不够），实测不是：**活都做完了，卡住的是审查**。8 处改动要在
审查者自己那一个上下文里核对，三次都没结出结论。硬拦的文案里把这条实测
写清楚了，同时说明它有旋钮（`limits --set review_limit=8`）——不是写死。

还有一条该记的：**审查那一步是这条链路上真正的薄弱环节**。它失败得很安静
（记成「没结论」），而「没结论」很容易被读成「派发不靠谱」。这一轮已经给
战绩加了说明，但根子在审查本身：它为什么在 8 处改动上结不出结论，还没查。
