# 怎么量才可信

回归集是用来判断「这次改动到底有没有用」的。量不准的话，后面每一次调优
都会变成猜。下面是踩过之后定下来的规矩。

## 本地 llama.cpp 必须用确定性配置

```bat
llama-server -m <模型> --port 8080 -c 8192 -ngl 99 -np 1 --cache-ram 0
```

`-np 1` 和 `--cache-ram 0` 不是为了性能，是为了复现。

默认配置（多槽位 + 提示词缓存）下，同一份提示词会因为服务端的缓存复用
状态不同而得到略有差异的数值，进而在近似并列处翻转采样。表现是：
同一道题、同一个模型、温度 0，两次跑出完全不同的轨迹。

实测过：加上这两个参数后，同一道题连跑三次，轨迹与生成的 diff 逐字节相同。

## 要比较就跑整批，不要跑单条

单条孤立跑的缓存状态取决于它前面发生了什么，所以**单条跑之间不可比**，
也不能拿去和整批里的同一条比。同一道题在孤立跑里过、在整批里挂，是正常的，
那不是任务不稳定，是起点不同。

结论：任何 before/after 的对比都要跑整批 25 题。

整批顺序跑本身是可复现的：同一份代码在确定性配置下跑两遍，25 条的结果
逐条相同，连 token 数都一样。

**但这条只在「起点相同」时成立。** 后来发现：两次 50 题的跑，代码没变、
任务顺序也没变，却有 1 道题来回翻（15_swapped_args）。原因是服务端的残留
状态——在同一台服务上先跑别的东西，再跑整批，第一道题的数值就可能不同，
然后顺着任务序列传导下去。

所以每次测量之前**重启 llama-server**，让起点是冷的。这不是洁癖：
不重启的话，±1 道题的差异会被误读成「这次改动有用」。

## 系统代理开着时，本机地址必须绕过它

Clash 开着（`ProxyEnable=1`）时，发往 `127.0.0.1:8080` 的请求会被代理拦掉，
实测直接 502。llama.cpp 客户端因此按地址判断：本机地址不走代理，
远程的仍然走。这条只在「用户的代理是开着的」时候才发作，最容易漏掉。

## 索引是有代价的增强，代价要封顶

索引入口原先只有一个 `try/except` 兜失败，**没有任何数量或时间上限**。
实测在一棵 40 万文件的目录树上：光遍历 4.4 秒、全量解析要几分钟外加一个
巨大的库——而它对「用 7B 改一处代码」的边际价值，超过一定规模后是负的。

更要紧的是一个具体机制：`iter_source_files` 原先用 `root.rglob("*.py")`
再过滤，**它先把整棵树走一遍**——跳过 `.venv` / `node_modules` 的名单等于
没生效，只在读文件那步省。改成 `os.walk` 时剪枝：前 2000 个文件的遍历
从 4.4 秒降到 0.03 秒。

现在三道闸门：先数一遍（只走目录不读文件，很便宜）再决定做不做；做的时候
仍有文件数与 20 秒预算两道上限。到量停下时按「没有索引」处理——**残的索引
比没有更糟**，查不到会被当成不存在。而且**明说给模型听**：预取文本里会写清
「本项目的代码索引不可用：项目里有 N 个 Python 文件，超过上限，符号类工具
因此没有提供，改用 read_file / search_code / list_dir」。
悄悄降级是最坏的选择。

这里还藏着一个会由上限本身引入的数据损坏：`index_project` 结尾会删掉
「本轮没见到」的文件记录，提前退出时 `seen` 是不全的，照删会把没走到的
文件全删掉。现在只有走完整棵树才清理。

## Gemini 那边仍然是一次采样

本地服务能锁死，云端不能——远程服务的批次组合不受我们控制。所以

- 本地：整批可复现，改动效果可信；
- Gemini：单次结果是样本，用来守「没被拖垮」这条底线够用，
  不要拿它的小幅波动当结论。

## 新增任务必须过完整性检查

`tests/bench/test_task_integrity.py` 会验证每个任务的原始代码都让验收失败。
一个本来就通过的任务毫无意义：它只会虚高分数，还会把「模型什么都没做」
伪装成「模型做对了」。

## 那 +997 token 是哪来的（不是督导）

上面最后两行差 997 token（2763 → 3760），但**这一批里督导一次都没被叫起来**：
回归集是小题（平均 2.1 步），撞不到 12 步上限，也凑不满「连续 4 次重复」或
「连续 8 步只看不写」。所以这批的结果与关掉督导**完全等价**——这一点由
0 次触发直接断定，不必再跑一遍对照。

真正的原因是这 26 个提交里往**提示词**里加的东西。每个请求都要付一次，
所以按「平均 2.1 次调用」放大：

| 加进去的东西 | token / 请求 |
|---|---|
| `dir_stats` / `calc` / `check_numbers` / `request_diagnosis` / `read_diagnosis` 五个工具 | 51 + 58 + 37 + 49 + 34 = 229 |
| 四条工作流提示（测量、算术、可读根、诊断） | 72 + 55 + 53 + 66 = 246 |
| 合计 | **475** |

475 × 2.1 ≈ **998**，与观察到的 997 对上。用真实分词器直接量当前系统提示：
正文只有 143 token，**工具清单 521 token**——工具一起有二十多个，它们
每轮都要把名字、描述、参数重述一遍。

这条规律值得记住：**往提示词里加能力 = 每个请求的固定税**。八个千 token 的
窗口下 475 token 是 7% 的有效预算，而它换来的能力（能测量、能算数、
能自查数字）大多只在少数任务里用得上。

## 把它收回来：工具改成索引，455 token/请求

同一批 50 题，只改一件事——提示词里不再写工具**整份说明**，改写成索引
（名字 + 参数名 + 一句干什么，按类别分组），完整说明用 `tool_help` 按需取：

| | 通过 | 平均步数 | 平均输入 | 总耗时 |
|---|---|---|---|---|
| 整份说明（15 个工具） | 50/50 | 2.14 | 3760 | 560s |
| 索引 + 按需 | 50/50 | 2.06 | **2868** | 430s |

索引 210 token，整份说明 665——**同一个注册表的口径**，省 455/请求。
两次都是冷启动服务后整批跑；耗时的差别受机器状态影响，别当结论，
**通过率不变、token −24% 才是**。

还有一层意义：现在的 2868 比换 27B 时的 2763 略高，但那时只有十二个工具，
现在有十五个还多了 `tool_help` 这套机制——**加工具不再线性地加税**，
下一个工具的成本从「整段说明 × 每个请求」降成「索引里一行 × 每个请求」。

## 第二条仪器：整批铺进一个工作区，全部交给一条会话

一题一会话（默认那条）量的是**单题能力**，而且它有个结构性盲区：
真实使用里没有「一道题一个新上下文」这回事。

所以另加一条：`bench --together` 把全部题铺成一个工作区——每题一个目录，
里面有 `TASK.md`（目标 + 判定方式）、起始代码、验收测试——**不给题目清单**，
告诉它题就在那个位置，让会话自己去发现、自己排序、自己验、自己收尾。

它量的是另外几件事：

- 任务发现：能不能自己从目录里读出「这题要干什么」；
- 自我排序：做完一道接着开下一道，还是原地绕；
- 长程：上下文重置之后还记不记得做到哪儿（状态块扛不扛得住）；
- 督导与派发：这两个机制第一次真正被用上。

**两条都要留着。** 一条掉分，另一条未必动；只看一条会得出相反的结论
（比如「改成索引之后 token 降了 24%」是第一条仪器量的，第二条仪器上
根本量不出来——它在几千步的尺度上）。

首次结果（50 题，27B，`--max-steps 12 --step-ceiling 120`）：

| | 结果 |
|---|---|
| 验收通过 | **9/50**（01–09，后面 41 道没开始） |
| 一条会话的账 | 62 步 / 66 次调用 / 167338 输入 token / 705s |
| 收尾方式 | 督导判断该收手（不是撞上限硬停） |

细节与它暴露的三个问题记在 dogfooding。

第二轮（加了「一批小活合成一次派发」的引导、并修掉客户端超时）：

| | 结果 |
|---|---|
| 验收通过 | **10/50** |
| 一条会话的账 | 72 步 / 76 次调用 / 255198 输入 token / 946s |
| `dispatch` | **0 次** |

两轮几乎一样，**但失效的样子完全不同**：第二轮它碰了 49 道题、写出的东西
却对不上（新建了名字像的文件、把目标文件的函数名「顺手改得更合理」）。
也就是说——**长任务的瓶颈不是步数、不是上下文、也不是没派发，是「不读就写」**。
证据与逐题对照记在 dogfooding。

**这条仪器值了**：它量出来的东西，一题一会话那条永远量不到（那边是 50/50）。

第三轮（验证范围跟着改动走 + 督导承担行动建议）：**跑完约第 80 步时人工停止**，
没有最终分数。停的原因是**它自己成了测量对象**——带范围的验证每步要起好几个
pytest 进程，长任务被明显拖慢（上一轮 72 步 / 16 分钟，这一轮 80 步 / 40 分钟）。

停下来之前的观察有价值：它**真的派发了**（两次，形状正是督导建议的那种
「按批交给子智能体」），而那两次派发暴露了链路里两个缺陷（审查者的证据包
没有范围、子智能体覆盖主循环检查点），都已修。细节在 dogfooding。

**下次跑这条仪器前要先解决它的速度**：把多个验证范围合成**一次** pytest
调用（传目录参数），而不是每个范围起一个进程。

**上面这条建议后来被实测否掉了。** 那 50 个目录里的测试文件**同名**（都叫
`test_acceptance.py`）：默认模式下同一 pytest 进程收集同名模块会报
import file mismatch；换 `--import-mode=importlib` 能解决同名，但同目录的
`from search import ...` 又失配（两种都实测过，都 ERROR）。所以省时只能
从别处来：

1. **跑前 N 道**（`bench --limit N`）——题集顺序稳定，前 N 道的结果和整批
   跑的前 N 道可以直接比；
2. 那次「慢了一倍」的归因也修正过：它**派发了两次**，每次十来个调用——
   那才是大头，不是 pytest 进程。

| 整批跑（50 题）的前 20 道，老措辞 | 9～10/20 | — | — | — |
| 目标改成「做到你确实做完的那一批为止」 | 5/20 | 6 | 14470 | 55s |
| 目标改成「尽量多做」 | 17/20 | 12 | 46716 | 182s |
| 验收测试改成工作区内唯一名 | 16/20 | 52 | 162733 | 610s |
| 唯一名 + 工具用法报错说清写法 | **20/20** | 60 | 204944 | 1068s |
| **先拆解、再逐步执行**（`--autonomous`） | **20/20** | 82 | 200964 | — |

**不要把这张表当受控实验**：这几行之间同时变了好几样东西（目标措辞、
验证范围、测试文件命名、工具报错文案、输出预算）。它证明的是**当前这一版
能做到 20/20**，不是「哪一项改动值 X 分」。

最后一行是另一条路：先 `decompose` 成带验收与范围的步骤、落盘，再逐步执行。
两条路的 token 量级一样（201K vs 205K），差别在形状——逐步执行每步是
独立上下文，所以步数更多（82 vs 60）但每次提示词更小。

### 为什么逐步执行快三倍：单位成本，不是总量

| | 一条会话自己安排 | 先拆解再逐步执行 |
|---|---|---|
| 验收 | 20/20 | 20/20 |
| 墙钟 | **1068s（17.8 分钟）** | **355s（5.9 分钟）** |
| 步数 / 每步耗时 | 60 / **17.8s** | 82 / **4.3s** |
| **工具调用** | **284** | **105** |
| 自动验证 | 15 次，共 10.6s（39 个范围） | 21 次，共 11.8s（22 个范围） |
| 输入 token | 204944 | 200964 |

**验证本身两边差不多**（10.6s vs 11.8s），所以快的原因不是「验证变便宜了」。
差在**每步做的事有多大**：一条会话里一步可能写 8 个文件、验 5 个范围；
逐步执行里一步就是一道题（读题目 → 读测试 → 改 → 验）。步数多了 37%，
但工具调用少了 63%、每步耗时少了 76%。

还有一层没分解清：**生成时间 vs 工具执行时间各占多少**。输入 token 只有
一半的信息——报告里原来漏了输出 token，现在加上了（`render_together`），
下次跑就能分开算。

这条对「先规划再行动」是**结论性的支持**：它的价值不在"更聪明"，
而在**把大任务切成小步**——小步的单位成本低得多（工具调用少、提示词小、
生成短），所以总墙钟反而更短。

值得单独记的一条：**它对自己的进度严重低估**。最后一次收手时它说
「未完成 01-08、11-14、16-20 共 17 题」，而客观验收是 20/20——它把大部分
已经写对的题忘了，因为状态块里的 `done` 只留最近 8 条。长任务里
**「我做到哪儿了」这件事需要一个不会被挤掉的载体**。

## 换一个更强的模型，满分

同一套编排、同一批 50 题，只把模型从 Qwen2.5-Coder-7B-Q8 换成
Qwen3.8-27B-UD-IQ2_S（2-bit 量化，7.8GB），结果 **50/50**，
而且平均步数 4.5 → 2.2、输入 token 6377 → 2763：**又快又省**。

这条把之前悬着的问题回答掉了：48/50 不是编排的上限，是 7B 的上限。
编排里的那些机制（强制收敛、自动验证、重复检测）在强模型上没有反作用，
省下的 token 反而更多——它不需要被推着走。

注意：这是带思考的模型，服务端必须加 `--reasoning off`，
否则推理内容会把输出预算吃光，表现为「模型返回了空内容」。

## 一条量出来的否定结论：片段替换工具

按「模型擅长整份重写、不擅长算行号」的推理，加一把 `replace_text`
（给出被替换的那一小段和新内容）看起来是显然的改进。实测相反：

取 6 道本来全过的题做子集，加上它之后 **6 道全挂（0/6）**，两次跑完全复现，
连 token 数都一致。它确实会被调用——坏在拼出来的片段本身，
比如 `try:` 下面少一个 `except`、缩进也不对。

结论：**这个模型擅长的是「交出一份完整文件」，不擅长拼片段。**
单发对照 50/50 用的正是前者。实现和单元测试留着（换模型时可以再量），
但默认不注册。

这条也说明子集是个好仪器：6 道题三分钟就能判一个改动，比跑整批快一倍。
整批只在确认和收尾时跑。

「工具摩擦」指这几类：`find_symbol` 收到文件名当符号名时只回一句「找不到」；
参数报错只列名字、不说用途（`path` 与 `pattern` 分属不同工具，模型会搬错）；
写测试文件时没有任何提示。三处都不是「工具给不出信息」，而是**信息给得不完整**，
各自对应一次可以避免的重试。

中间有一版跑到 22/25。**不要把这个差值当结论**：同一套解码是确定性的，
但轻微改写提示词会让 1–2 道题来回翻，20 与 22 之间就是这个噪声。
要判定一个改动的真实效果，得让每个配置跑两三遍，或者把任务集再扩大。

有一点不受噪声影响，因为它跨了两条线同时变化：**「自称完成」从 5/25 涨到
22/25**。它反映的是模型能不能接上「我改的 → 测试通过 → 收尾」这条因果链，
不是某一道题的运气。虚假完成（自称完成但验收失败）同时从 3 条降到 1 条。

注意第二条基线是在 Gemini 那一栏还没重测的情况下记的——当时本机代理整个
不通（google/github 全部连不上），云端基线暂时沿用上一版。

同一批题不走 Agent、直接把文件内容给模型要它一次改完，是 **25/25**。
所以「本地模型只有 17/25 的能力」这个说法是错的——那道分界线划在编排上，
不在模型上。

改之前本地那 17 条里，有 15 条是被 12 步上限截断的——改动早就提完了，
模型不肯收尾。把上限压到 5 步只掉 1 条，说明多出来的 7 步只换来 1 道题。

**上面这些行现在读法变了**：那时步数是硬截断，撞上即失败。现在撞上限会先问
督导（见 dogfooding「撞上步数上限不再等于失败」），所以「被上限截断」这件事
本身不再等于失败。要用回归集判断效果，得在改动前后各跑一遍整批——
跨过这个改动去和旧数字比，比的是两套不同的机制。

## 重复测量：同一批 5 题，各跑三遍

上面那些对照都是**单跑**。单跑能不能当结论，只有重复过才知道。规程定成：
每遍冷启动 llama-server、工作区复原、同一条目标文本，跑三遍取中位数。

| 仪器 | 每遍（三遍相同） | 通过 |
|---|---|---|
| A 一题一会话（`bench --limit 5`） | 10 次调用 / 15790 输入 token / 模型 31.7s | 5/5 |
| B 整批一条会话（`run --autonomous --limit 5`） | 16 次调用 / 34528 输入 token / 模型 61.3s | 5/5 |

两条结论：

1. **长任务贵在轮次，不在工具。** 工具那一笔两边都在 3 秒内，差额全在模型。
   A 每题 2 轮；B 五步里两步 3 轮、一步 6 轮——多出来的轮次清一色是
   `read_file` / `list_dir`，也就是**自己去翻文件**。翻什么？见 dogfooding
   第三刀：翻的是它本来就已经知道的那个文件。
2. **同一套代码的重复是稳定的**（逐 token 相同）。所以「改动前后差在哪」
   可以信；但**跨代码状态**引用数字不行，见下。

### 一条复现不出来的历史数字

本文档原先记着「两刀之后：12 轮 / 26995 token」。按上面这套规程复跑，
同一套**已提交**的代码、同一批题，跑出来是 16 轮 / 34528，连跑三遍都一样；
把目标文本换回归档里的 `TOGETHER_GOAL` 再拆解一次，产出的计划逐字相同——
所以差别不是目标文本带来的。

能确定的只有时间线：那次跑在 10:15，对应的提交在 10:16，中间有 18 秒空档，
最可能是**提交前的工作区版本**和提交后的不完全相同。

教训写进规程：**单样本数字必须连代码状态一起记**，不许跨状态引用；
判定一个改动的效果至少三遍、取中位数，并写明跑的是哪个提交。

### 剩下来的那笔「记账税」

第三刀（见 dogfooding）之后 B 是 11 轮 / 24683 token，A 是 10 轮 / 15790，
差距里还有一笔每轮都要付的固定开销。量法：把两边首轮提示词按区段拆开数
（同一套装配、同一个分词器）——

| 区段 | A 单题首轮 | B 长任务·步骤首轮 |
|---|---|---|
| 系统提示（含工具表） | 1614 | 1614 |
| 状态块（目标 / 进度） | 44 | **239** |
| 预取（符号表 + 正文 + 锚定） | 101 | **296** |
| 任务 / 步骤提示词 | 41 | **236** |
| 首轮合计 | 1759 | **2149** |

系统提示两边**一模一样**，差别全在后面三处：B 每轮多付约 390 token（+22%），
11 轮合计约 4300 token，占 B 总量的 17%。

这是长任务的**记账税**：目标、进度、契约、范围都得跟着每一轮走。要再往下压，
动的就是这三处——每一处都有它的用处，没量过之前不算数（比如状态块是
「我做到哪儿了」的唯一载体，砍它不是省钱，是把长程能力砍掉）。

### 第三条仪器：五十题走「拆解 + 逐步执行」

前两条仪器（一题一会话、整批一条会话）都不是自主编排那条路。第三条是
`run --autonomous --limit 50`：先把 50 题拆成步骤，再逐步执行、逐步验收。

| | 结果 |
|---|---|
| 计划 | 49 步（**漏了 50_retry_count**：目标说 50 件事，它排到 49 停手） |
| 验收 | **42/50**（第 43 步没做完，计划在那里中止，44–49 没试） |
| 一条会话 | 267 次调用 / 420948 输入 + 33768 输出 token |
| 单步 | 平均 6.2 轮 / 9789 输入 token（拆解把多数步骤标成了 `subagent`） |
| 墙钟 | 约 28 分钟（按工作区文件的写入时间推的，不是我数等待次数估的） |
| 时间账 | 只有 206.9s 是可信的——**派发路径没记时间**，这是个缺口 |

这一跑的价值不在分数，在两件事：它当场暴露了「拆解的输出预算装不下 50 步」
（`run` 直接回一句「没能拆出任何带验收标准的步骤」退出），也暴露了
「无人值守下一条越界会把同批里对的改动一起作废」。两条都记在 dogfooding。

**它教不会的东西**：单跑不能用来判「改快了多少」。要判快慢还是用 5 题
跑三遍取中位数——第三条仪器贵，只用来做规模检查。

### 那 42 万 token 花在哪儿：一笔一笔拆

同一批 50 题、同一个模型，两条路摆在一起：

| | 一题一会话（A） | 自主编排（B） |
|---|---|---|
| 验收 | **50/50** | 42/50（第 43 步中止） |
| 调用 | 112 | **267** |
| 输入 token | 141017 | **420948**（另有 33768 输出） |
| 墙钟 | 390s（6.5 分钟） | 约 28 分钟 |

B 不只是「慢一点」。把 B 拆开（同一个脚本按步统计）：

| 组成 | 步数 | 调用 | 输入 token | 每步 |
|---|---|---|---|---|
| 拆解 | — | 3 | 约 13k | — |
| 自己做的那几步 | 14 | 43 | 120792 | 3.1 轮 / 8628 token |
| 派给子智能体的那些步 | 29 | 224 | 300156 | 7.7 轮 / 10350 token |

两条结论都是实算的，不是估的：

1. **「已完成」那一行吃掉 31% 的输入**：132165 / 420948。它把前面每一步的
   目标全文列出来，随进度线性增长，而**每一次调用**都带着它。状态块里本来
   就有一份按标定值截断的版本（最近 8 条 + 指向 `progress.md`），那一行是
   重复付款。已改成只列最近几条。
2. **派发把轮数翻倍**：自己做 3.1 轮/步，派发 7.7 轮/步——一次派发 =
   实现 + 独立审查 + 判定（打回还要再来一轮）。29 步派发多出约 133 次调用；
   按本轮实测约 6 秒/次，**约一半的墙钟来自这个路由选择**，而它没换来更高
   的通过率（派发的那 29 步里照样有没做完的）。判据已按「这一步要碰几个
   文件」写具体。

两条改动的**预期**（同一批调用、更小的提示词）：输入 token 少约 31%，
调用次数少约一半 → 50 题那一轮有望从 28 分钟落回 12 分钟上下。
**这是推算，不是测量**——要确认只能再跑一轮 50 题。

### 复测：同一批 50 题、同一条目标，改完之后

| | 改前 | 改后 |
|---|---|---|
| 验收 | 42/50（第 43 步中止） | **49/50**（49 步全做完；差的 `50_retry_count` 压根没进计划） |
| 调用 | 267 | **143** |
| 输入 token | 420948 | **379616** |
| 输出 token | 33768 | **13252** |
| 每步 | 6.2 轮 / 9789 token | **2.9 轮 / 7747 token** |
| 派发 | 29/43 步 | **0** |
| 墙钟 | 约 28 分钟 | **约 22 分钟**（11:48→12:11） |

三件事得到了确认：

1. **派发判据那一刀有效**：29/43 → **0**。49 步全部 `self`，每步轮数
   6.2 → 2.9，输出 token 少了 60%。
2. **「已完成」那一刀有效，但没有推算的那么大**。按这次的调用规模算，
   那一行原本要 78078 token；不砍的话这次是 457694，也就是省了 **17%**。
   推算时说的 31% 是拿**改前那次**的调用次数（267）算的——一行的成本正比于
   调用次数，而调用次数同时也被砍掉了一半，所以占比自然缩水。**这是推算
   与实测之差的一个教训：先问「这个量跟什么成正比」。**
3. **墙钟 28 → 22 分钟、通过 42 → 49**。每步墙钟 32.6s → 20.6s。

还没解决的：

- **计划少了第 50 题**（两次跑都漏）。提示词说「把 50 道题都做对」，
  它排到 49 停手。这要一道**覆盖检查**（工作区 50 个目录 vs 计划覆盖 49），
  属于验证该干的活。
- **拆解自己占 5.5 分钟**（墙钟的 1/4）：3 次调用生成 50 步的完整 JSON，
  输出量跟 49 步执行加起来差不多。
- **每次调用的提示词还是 A 的 2.1 倍**（2655 vs 1259 token）：系统提示两边
  一样（1614），差在状态块、预取、步骤提示词，以及**步内的历史**——
  B 的每一步会真的去读文件（TASK.md、验收测试），读到的内容留在历史里，
 后面每一轮都带着它。A 的题面由人写好，不需要读。

### 第三次：覆盖检查 + 拆解账 + 历史去重，一起上

| | 第一次 | 第二次 | **第三次** |
|---|---|---|---|
| 验收 | 42/50 | 49/50 | **50/50** |
| 计划步数 | 49（漏 1 题） | 49（漏 1 题） | **50（一题不落）** |
| 调用 | 267 | 143 | **147** |
| 输入 / 输出 token | 420948 / 33768 | 379616 / 13252 | **398258 / 13323** |
| 每步 | 6.2 轮 / 9789 token | 2.9 轮 / 7747 token | **2.9 轮 / 7965 token** |
| 派发 | 29/43 步 | 0 | **0** |
| 墙钟 | 约 28 分钟 | 约 22 分钟 | **约 16 分钟**（12:30→12:46） |

这一轮验证了三件事：

1. **覆盖检查有效**：计划从 49 步变 50 步，验收第一次到 50/50。第三次的
   拆解不需要补排（模型自己排满了 3 批），所以这条能力这轮是「没派上用场」，
   但上一轮那份 49 步的计划如果当时有这个检查，会当场被指出来。
2. **拆解那笔账看得见了，而且第一眼就抓到一个 bug**：单独跑 `plan` 时打出
   `9 次调用 / 38451 输入 / 327s`，而我的分批设计只该用 3 次。原因是
   **被截断时我把整段的 budget 砍半**了，后面的批次一路变小。改成只压下一批
   之后，同样的 50 步：**3 次调用 / 13126 输入 + 4957 输出 / 148s**——
   输入少了 3 倍，墙钟少了 3 分钟。本轮正式跑打印的就是这一行。
3. **历史去重没有生效**（实测命中 0 次）。设计是「工具输出与提示词里已有
   正文完全相同时只留一行」，但模型这一轮读文件主要走 `survey`（38 次），
   它的输出是**几个文件打包**，整段匹配自然对不上。所以这条是**没量到收益**：
  保留实现与单测（读同一个文件两次的场景它是对的），但别把它算进收益。

三条一起上之后的账：50 题一题一会话是 6.5 分钟 / 141017 token / 50 比 50，
自主编排是 **16 分钟 / 398258 token / 50 比 50**。每步 2.9 轮已经接近单题
模式的 2.2 轮，剩下的差在两处：**每次调用的提示词是 A 的 2.1 倍**（2655 vs
1259），以及**拆解自己那 2.5 分钟**（占墙钟六分之一，是生成 50 步 JSON 的
固有成本——5k 输出 token，按本机实测约 33 token/s）。

### 那 4.6 秒/步的残差：拆了两刀，只解释了一小半（诚实记录）

50 题那轮：墙钟 936s − 模型 666.5s − 工具 37.6s = **232s 没人认领**，
折合约 4.6 秒/步。怀疑过两处，都真测了：

| 怀疑 | 测法 | 结果 |
|---|---|---|
| 每步重建循环（建索引、装注册表、算预取） | 假模型跑 50 步自主编排（模型时间≈0） | **0.04 秒/步**，50 步才 2 秒——不是它 |
| 分词计数：每次 `count()` 都是一次 `/tokenize` 往返 | 假 /tokenize 数往返 + 真服务测延迟 | 3 步里 36 次 `count()` → 10 次真往返（缓存省 72%）；单次往返实测 **23～26ms**；推算整轮约 1760 次 × 25ms ≈ **44 秒** |

两处加起来约 46 秒，**还剩约 185 秒没有解释**。所以：

- 分词缓存是**该修**（44 秒是白花的，而且每次运行都付），已修；
- 但"4.6 秒/步"这个数字本身来自**残差**，不是测量。下一次要动它，得先在
  循环里装每阶段的计时器（装配 / 预取 / 落盘 / 校验），而不是继续猜。

### 残差拆完了：它是**两笔**，不是"神秘开销"

装了分阶段计时器之后（循环里：装配上下文 / 工具 / 验证 / 落盘 / 督导；
调用方补：装配循环 / 收尾），5 题那轮每一步的账长这样（真模型）：

```
本步墙钟 36.9s ｜ 模型 33.1 装配循环 0.4 装配上下文 0.4 工具 0.5
                验证 2.4 落盘 0.0 收尾 0.0 其它 0.2
本步墙钟  9.7s ｜ 模型  8.4 装配循环 0.3 装配上下文 0.3 工具 0.0
                验证 0.5 落盘 0.0 收尾 0.0 其它 0.2
```

也就是说：**每一步里，编排自己只花 1～3 秒，模型占 85% 以上**。

那 50 题那轮的 232 秒残差是怎么来的？重新对账——

| 项 | 数值 |
|---|---|
| 整轮墙钟 | 936s |
| 其中**拆解那一阶段** | 148s（它不属于任何"步"，原先没算进任何一笔） |
| 步的墙钟 | 788s |
| 步内模型 | 666.5s |
| 步内工具 | 37.6s |
| 剩下的编排开销 | 84s ≈ **1.7 秒/步** |

148 + 84 = 232 —— 与残差完全对上。**"4.6 秒/步"是个测量错误：我拿整轮墙钟
去减只包含步内的时间，把拆解那 148 秒摊到了每一步头上。** 教训记下来：
残差不是结论，先让它逐项对得上账；对不上就说明还漏了某一项（这次漏的是
"不属于任何步的那一段"）。

于是这条轴上的优化基本到头了：**墙钟的大头是模型，而模型的时间大头是
预填充（输入 token）**——所以真正剩下的杠杆只有"每次调用的提示词"那 2.1 倍，
不是编排开销。
