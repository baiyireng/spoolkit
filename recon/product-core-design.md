# spoolkit 产品核心设计：任务执行控制台

## 一句话

**spoolkit 不是“和 Agent 聊天”，而是“把一次请求变成可执行、可观察、可干预、可回放的任务”。**

聊天是入口，任务才是产品的一等公民。

## 为什么现在像 demo

内核并不弱：ReAct 循环、督导、自动验证、重复拦截、上下文压缩、工具权限都已经有。
但产品表面只暴露了：

- 消息气泡
- 一段被压扁的 trace
- 最终答复
- 少量 tool 事件

于是用户看到的是“模型说了什么”，而不是：

- 它正在做什么
- 为什么这么做
- 做到了哪一步
- 哪些证据支持
- 哪里需要我批准
- 失败后能不能恢复
- 这个任务以后还能不能找回来

这不是视觉问题，是**产品对象缺失**。内核丰富，产品表面贫瘠。

## 核心对象模型

建议把产品对象定成：

```text
Workspace
  Session
    Task            # 用户的一次目标
      Run           # 一次执行尝试（可重试/恢复）
        Step        # 一次模型调用 / 循环迭代
          Intent    # 为什么做
          Action    # 工具调用
          Observation
          Decision  # 继续 / 改道 / 收尾 / 督导
        Approval    # 人工确认
        Verification
        Artifact    # 文件、diff、命令、URL
      Final
```

当前代码里的 `AgentTurn` 是**模型的一步**，不是用户的一轮任务。
产品层必须区分：

- Task：用户要什么
- Run：这次执行
- Step：模型的一次决策
- Action/Observation：工具调用与结果

## 两个投影，不要混

同一份事件日志，面向两个消费者：

### 模型投影

只给模型：

- 当前目标
- 最近 N 个动作的 intent
- 结果 summary
- 未决问题
- 失败/下一步
- 必要证据

不给：

- 完整 thought
- 大段 raw tool output
- 全部历史事件

### 用户投影

给 UI：

- 任务时间线
- 工具卡
- 结果摘要 + 可展开 raw
- 证据引用
- 审批 / 验证 / 失败 / 重试
- 最终答复
- 任务状态和操作

**事件日志是源，模型投影和 UI 投影是两份不同的视图。**

## 思维链的定位

- `thought` 是模型内部推理，不是产品主内容；
- `intent`（工具调用的 why）是面向人的“为什么做”；
- `assessment` 是面向人的“对督导建议的表态”；
- 原始 thought 默认折叠/仅调试，不进入主对话流，也不长期回灌上下文。

产品展示的是**决策与证据**，不是内心独白全文。

## 预期对话流

外层仍是聊天：

```text
用户：修复 snake.html 食物刷新逻辑
```

内层是任务卡：

```text
▾ 任务 · 4 步 · 2 个文件 · 验证通过

  01 定位
     意图：先看 reset/placeFood 的实现
     读取 snake.html        ✓
     证据：snake.html:98

  02 修改
     替换 placeFood 赋值     ✓
     diff +1 -1

  03 验证
     自动验证 · node --check ✓

  04 结论
     已修复：食物被吃后会重新生成

▸ 助手答复
```

展开后才有：

- 参数摘要
- 原始工具输出
- diff / 命令
- 失败原因与重试
- 督导介入
- 上下文压缩/验证等系统事件

默认不是日志倾泻，而是**渐进披露**。

## 正式产品必须回答的问题

用户在使用任何一个任务时，应该能回答：

1. 它现在在做什么？
2. 为什么这么做？
3. 做到哪一步了？
4. 哪些文件/命令/证据被碰过？
5. 哪里需要我批准？
6. 失败了没有？能不能重试/恢复？
7. 结果验过没有？
8. 这个任务以后在哪里找回来？

现在的聊天流只能回答第 8 个的一部分（会话），其余都靠读长文。

## 设计原则

1. **Task-first，chat-second**
2. **事件源，投影视图**
3. **证据优先于叙述**
4. **渐进披露，不默认倾倒日志**
5. **人在风险点介入**：审批、停止、重试、恢复
6. **任务可持久化、可回放、可恢复**
7. **模型上下文与 UI 数据分离**
8. **状态机明确**：queued/running/waiting/approval/verifying/done/failed/cancelled

## 对当前路线的影响

- B0 不只是量 token，也要盘点 Task/Run/Step/Action 的对象缺口。
- B1 不只做 ToolResult，还要定义 TaskEvent / Task / Run 的身份与状态。
- B2 不只迁移工具，还要让 runner 持久化事件，而不是只留 40 行 trace。
- B3 做任务时间线，不先做气泡美化。
- B4 补产品表面：任务列表、审批、artifacts、历史/搜索。
- B5 再做视觉系统。

**第一个真正的产品里程碑**：
“一个任务卡能完整显示 intent → action → observation → decision → final，并且刷新后还能找回。”
做到这个，demo 感会明显下降；只做视觉不会。
