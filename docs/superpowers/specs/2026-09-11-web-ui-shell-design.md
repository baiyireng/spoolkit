# Web UI 壳 —— 设计文档

日期：2026-09-11
状态：待评审

---

## 1. 背景与目标

### 1.1 要解决的问题

当前 agent 只有命令行界面。它已经能自己拆解目标、改代码、在隔离副本里验证、按策略自动落盘，但**所有交互都发生在终端里**：你要盯着滚动的纯文本判断一次改动该不该应用，diff 长了要往回翻，任务跑完只剩一片可以滚回去的历史。

这个壳要解决的就是**「看 diff 然后决定」这一步**。

### 1.2 目标

在浏览器里提供：实时看到 agent 在做什么、清晰地看到待确认的改动、点一下就应用或拒绝。

**不做**：重写内核、引入前端框架、做实时协作、多用户。

### 1.3 定位：B 起步，留 C 的口子

三种可能的定位——只看（A）、看 + 确认（B）、全操作（C）。

选 B：**确认是唯一真正需要图形界面的地方**。在终端里敲任务并不比网页慢，「切策略」一个月也用不上几次，为它们搭界面不划算。

**但实现时发现，B 和 C 在核心机制上几乎没差别。** 要让浏览器看到实时运行并接受确认，服务端必须拥有那个子进程；而一旦它拥有，页面上加一个输入框的成本几乎为零。所以第一版直接包含输入框，剩下的差别（会话切换、策略编辑）留到以后。

---

## 2. 核心决策

### 2.1 子进程边界，不进程内嵌

壳**不 import 内核**，而是起子进程跑 CLI。

| | 子进程 | 进程内嵌 |
|---|---|---|
| 内核崩溃时 | 壳存活，你能看到崩在哪，能再发任务 | 界面跟着一起没 |
| 复用既有能力 | 直接复用 CLI 全套 | 要重新装配一遍 |
| 数据结构化 | 需要事件协议 | 直接拿对象 |
| 复杂度 | 一个管道 | 回调机制 |

**选子进程。** 我们花了很大力气让主循环能从失败里恢复（截断重试、解析失败回灌、上下文重置），进程内嵌会让这些努力白费——**内核崩一次，界面跟着一起没**。子进程边界是免费的隔离。

### 2.2 零新依赖

后端用标准库 `http.server`，前端一个不打包的静态页面。

理由：内核零依赖意味着它能在任何有 Python 的地方跑；而**壳本来就是你本机开的东西**。整个项目里最不应该重依赖的一层就是这层。满打满算六七个路由，引入 ASGI 全家桶是拿大炮打蚊子。

实现上要留意两点，写代码时不能踩：`http.server` 默认单线程，必须用 `ThreadingHTTPServer`（否则一个 SSE 连接就把服务堵死）；SSE 的保持连接要手工管，写完 flush、别让缓冲把事件攒住。

### 2.3 事件协议：新增 `--events` 模式

现在的 CLI 输出是给人看的散文。加一个 `--events` 模式输出 JSON 行——**同一个主循环、同一套工具、同一份记忆，只是换了个打印器**。

**为什么必须结构化，而不是让 UI 解析散文**：如果 UI 靠识别「应用这些修改吗？」这串字判断该不该出按钮，那么把提示语改一个字，按钮就再也不出现了——**而界面上不会报错**。人会先去查网络、再查浏览器，最后才想到是文案变了。用事件，文案随便改。

**附带收益**：`--events` 让一次运行可以被完整录制（JSON 行文件），回归集和调试都能用。现在一次任务的过程除了终端滚过去就没有别的记录了。

### 2.4 一次只跑一个运行

本地单人在用。并发带来的状态同步、多个待确认队列的合并，问题价值远低于复杂度。服务检测到已有运行在跑就拒绝第二次，并明确说明。

**这是有意的简化，不是遗漏。** 写进文档是为了避免以后有人把它当 bug 修。

### 2.5 前端薄，逻辑在后端

前端不做自动化测试，靠人工验收。这是取舍：为一个壳搭浏览器测试套件，成本远高于它挡住的问题。

代价必须说清楚——**前端出错只能靠人看出来**。所以前端要尽量薄：不持有状态、不做业务判断，只负责渲染事件和发三个请求。所有逻辑放在后端，那里能测。

## 3. 架构

```
浏览器
  │  HTTP + SSE
  ▼
agents-dev serve（标准库 http.server，ThreadingHTTPServer）
  │
  │  POST /run 起子进程；写 y/n 到 stdin
  ▼
agents-dev run --events（既有 CLI + 事件输出器）
  │
  ▼
Agent 内核（一行不改）
```

**数据流**：浏览器 `POST /run` → 服务起子进程 → 子进程按行吐 JSON 事件 → 服务解析并广播给所有 SSE 客户端 → 浏览器渲染。当出现 `await` 事件时界面出按钮；点击 → `POST /confirm` → 服务往子进程 stdin 写 `y` 或 `n`。

---

## 4. 事件协议

子进程 stdout 上，**一行一个 JSON 对象**。非 JSON 行一律忽略——内核偶尔会打印别的（比如第三方库的警告），不能因为一行杂音让整个流断掉。

| type | 字段 | 含义 |
|---|---|---|
| `start` | session, goal, policy, window | 运行开始 |
| `step` | n | 进入第 n 步 |
| `tool` | name, ok, detail | 一次工具调用结束 |
| `diff` | path, text | 待确认的改动 |
| `await` | count | 等待用户确认，界面在此出按钮 |
| `usage` | steps, calls, prompt_tokens, completion_tokens | 用量摘要 |
| `final` | ok, text | 运行结束 |
| `error` | message | 可恢复的错误说明 |

**`await` 是双向协议里唯一需要浏览器回话的事件。** 其余全是单向广播。

## 5. HTTP 接口

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| GET | `/` | — | HTML 页面 |
| GET | `/events` | — | SSE 流。**每建立一次连接，首帧就是当前状态快照** |
| GET | `/state` | — | 同一份状态快照，单独取一次（页面初始化与调试用） |
| POST | `/run` | `{"goal": "..."}` | 202 已启动 / 409 已有运行 / 400 参数不合法 |
| POST | `/confirm` | `{"apply": true}` | 200 / 409 当前没有待确认 / 400 |

状态快照包含：是否有运行在跑、在跑什么、有没有待确认、最近的用量。

**为什么 SSE 首帧要发快照**：`EventSource` 断线会自动重连，而重连期间发生的事件**不会补发**。如果连接建立后只等新事件，页面重连后会停在断线前那一刻的样子——**运行其实还在继续，但你会以为卡住了**。每次连接先给一份完整快照，重连就自然恢复了。

`/state` 存在的理由是另外两个：页面初始化时还没建立 SSE，以及调试时用 curl 一眼看当前状态。它和 SSE 首帧返回的是同一份数据，不是两套逻辑。

## 6. 界面结构

选定 B 布局：左右分栏，**右侧的待确认面板固定，不随输出滚走**——要判断的时候视线不用移动。

```
┌──────────────────────────────────────────────────────┐
│ demo · auto · 32768          [ 任务输入…        ][开始]│
├────────────────────────────┬─────────────────────────┤
│ 左：事件流（自动滚动）       │ 右：待确认               │
│  step0 find_symbol → 成功   │  1 处改动               │
│  step1 replace_lines → 成功 │  ┌───────────────────┐  │
│  step4 run_command → 成功   │  │ + def add(a: int) │  │
│                            │  │ - def add(a, b)   │  │
│                            │  └───────────────────┘  │
│                            │  [应用]  [拒绝]          │
│                            │ 空闲时显示最近记录        │
└────────────────────────────┴─────────────────────────┘
```

视觉风格不在本次范围内——先把结构跑通，样式后再调。

## 7. 错误处理

四种情况，每一种都必须有明确行为：

| 情况 | 行为 |
|---|---|
| 子进程崩溃或非零退出 | 服务不死，广播 `final(ok=false)` 与错误摘要 |
| SSE 断线 | 浏览器自动重连，重连后拉 `/state` 补状态快照 |
| 子进程长时间无输出 | 界面保持「运行中」，不假装完成 |
| 确认按钮被重复点击 | 点击后立即禁用；服务端对无待确认的请求返回 409 |

最后一条不是洁癖：**重复往 stdin 写 `y`，会让后续的 `input()` 拿到意外的输入**，那类错位极难定位。

## 8. 测试策略

**能自动测的**：

- 事件解析：喂一段混合输出（散文 + JSON 行混杂），断言只提取出 JSON 事件
- 路由：起服务、发请求、断言状态码与响应体
- 确认流程：用假子进程，验证写了 `y` 之后流程继续、写了 `n` 之后不落盘
- 状态快照：运行中/空闲/待确认三种状态下 `/state` 的返回
- 并发拒绝：第二次 `POST /run` 返回 409
- 子进程崩溃：验证服务存活且广播了失败事件

**明确不测的**：前端渲染。取舍见 2.5，代价是前端问题只能靠人看出来。

## 9. 文件结构

| 文件 | 职责 |
|---|---|
| `src/agents_dev/cli/events.py` | 内核侧的事件输出器（`--events` 用） |
| `src/agents_dev/web/server.py` | HTTP 服务、路由、SSE 广播 |
| `src/agents_dev/web/runner.py` | 子进程生命周期与确认写入 |
| `src/agents_dev/web/protocol.py` | 事件解析与序列化（刻意不叫 events，避免与内核侧同名） |
| `src/agents_dev/web/page.py` | 内嵌的单页 HTML（字符串常量） |
| `src/agents_dev/cli/commands/serve.py` | `serve` 命令 |

页面内嵌成 Python 字符串，而不是外置 HTML 文件：**这样跑起来只有一个东西要分发**，也避免打包时漏文件。代价是编辑时没有语法高亮，可以接受。

## 10. 分阶段

| 阶段 | 内容 | 验收 |
|---|---|---|
| 1 | `--events` 输出器 | 跑一次任务，stdout 是干净的 JSON 行 |
| 2 | 服务端：路由、SSE、子进程管理 | 用 curl 能发起运行并收到事件流 |
| 3 | 前端页面：事件流 + 待确认面板 | 浏览器里能跑通「发任务 → 看输出 → 确认」 |
| 4 | 错误路径：崩溃、重连、重复点击 | 四种情况逐一人工验证 |

## 11. 明确不做的事

| 不做 | 原因 |
|---|---|
| 引入 Web 框架 | 六七个路由撑不起；见 2.2 |
| 前端构建步骤与框架 | 前端要薄；见 2.5 |
| 并发运行 | 单人使用，复杂度不划算；见 2.4 |
| 会话切换、策略编辑 | 留到以后；见 1.3 |
| 远程访问与鉴权 | 只绑 `127.0.0.1`，本地单人用 |
| 前端自动化测试 | 取舍见 8，代价已写明 |
| 视觉风格与动效 | 先把结构跑通 |

## 12. 待验证的假设

1. **标准库 `ThreadingHTTPServer` 能稳定支撑 SSE**——需要实测长连接下的表现。
2. **子进程按行吐 JSON 不会因为内核的杂项输出而错乱**——需要在真实运行里观察。
3. **`await` 与 stdin 写入的时序可靠**——写早了或写晚了都会错位，需要实测。
