# 本地小模型编程特化 Agent —— 设计文档

日期：2026-09-11
状态：待评审

---

## 1. 背景与目标

### 1.1 要解决的问题

用本地运行的小模型（7B 级、4bit 量化）驱动一个编程 Agent，在**受限的上下文预算**（目标 4K–8K 有效 token）下完成真实的中小型代码修改任务。运行环境为单张 12GB 显存的消费级显卡，模型经由 llama.cpp 提供服务，全流程本地、离线、无外部 API。

### 1.2 为什么值得做

当前主流 Agent 方案默认「上下文大到用不完」：动辄 128K 窗口、动辄把整个文件甚至整个仓库塞进提示词。这个假设在本地小模型上完全不成立——显存决定了上下文长度，模型能力决定了它对长上下文的利用率。而小模型塞满上下文后质量下降的幅度，比大模型剧烈得多。

所以本项目不是在复刻一个云端 Agent 的缩水版，而是针对「小模型 + 短上下文」这组约束做专门设计。

### 1.3 项目性质

学习型项目。核心机制（主循环、上下文装配、记忆读写与检索、工具协议、子智能体运行时）全部手写，以保证可观察、可修改、可调试；基础设施（HTTP 客户端、CLI 渲染、测试框架）使用成熟库。不引入封装了 Agent 主循环的框架。

## 2. 核心设计原则

以下六条贯穿全部设计。当具体实现出现分歧时，以这些原则为准。

### 2.1 状态外置，历史可弃

主循环真正需要的是「我做到哪了」，而不是「我们聊过什么」。因此任务状态以结构化形式外置存储，每轮注入；一旦状态被外置，对话历史就变成了可以随时丢弃的废物。

这直接给出了「短上下文」的实现路径：**不是压缩历史，而是让历史不再必要。**

### 2.2 精确取用，而非整份塞入

省 token 的从来不是「把仓库变成索引」这个动作，而是「用索引做相关性排序，只把最相关的极小片段送进上下文」。索引层若没有配套的排序与裁剪，只会成为更大的负担。

### 2.3 约束必须可检验，不能只被要求

小模型不会遵守提示词里的软性约束（「请保持函数简短」）。它只对**具体的、指向性明确的反馈**作出反应（「`_parse_file` 有 62 行，超过 40 行上限，第 41–62 行是独立的解析步骤，建议抽出」）。

因此所有结构约束都通过独立的检查器实现，检查结果作为反馈回灌，而不是写在提示词里祈祷模型遵守。

### 2.4 离线会话吃大预算，主循环吃小预算

主循环的预算之所以紧张，是因为它同时携带状态、历史、工具结果、当前代码，注意力被摊薄。而离线会话（预读、归纳、检索）是一次性的，可以把全部预算花在一件事上。

于是形成一条杠杆：**主循环上下文卡死在 8K，离线会话可以开到 32K 甚至更大**，两者之间只传递浓缩结果。记忆归纳、文件预读、任务分派说明的撰写，都是这条杠杆的应用。

### 2.5 同一模型，多上下文；子智能体是一次性容器

子智能体**不是**第二个模型，而是同一个 llama.cpp 服务上的独立干净上下文，配专属提示词与受限工具集。因此不额外占用显存。

子智能体的核心价值不是并行（单 GPU 下不会真正并行），而是：**它是一次性容器，上下文满了可以直接丢弃重来，代价仅为重派一次任务。** 主循环若上下文溢出，代价是整个任务状态丢失。两者代价不对等，所以应把会膨胀的工作放进可丢弃的容器里。

### 2.6 零依赖优先，能力按需引入

每引入一个依赖都要有明确理由，且必须能在缺少它的情况下降级运行。代码解析先用 Python 标准库 `ast`，记忆检索先用 SQLite 内置的 FTS5，向量检索、多语言解析、多模态能力均先留接口、后按需实现。

理由：在没有测量数据之前，无法判断这些能力是否真的带来收益。先跑通、先测量，再决定。

### 2.7 能力标定与安全边界要分开

系统里有六十多个数字常量，它们不是一类东西。判据只有一句：

> **这个数字只会因为模型更强而被突破吗？**

**是 → 它是能力标定，必须可调，默认不该压低。** 步数上限、批大小、预算比例、
截断长度、重复检测阈值都属于这一类。它们存在的理由是「在弱模型上防止退化」，
而**同一个数字用在强模型上就是天花板**。外部 API 的窗口、预算与判断力都比
本机小模型强得多，替它砍掉能力是纯损失。

**防的是不可逆后果 → 它是安全边界，写死。** 路径不出工作区、永久禁止清单、
命令超时上限、遍历条数安全网：这些防的是「做坏事/挂死」，与模型强弱无关。

取值优先级按这个顺序，而且是单向的：

```
命令行/配置  >  供应商探测（窗口、真实分词）  >  运行中的证据（截断、战绩、督导）  >  保守默认
```

两条配套要求：**来源要可查**（每个生效的值都能说出来它从哪来、被谁覆盖，
否则「它为什么只派 5 件」会变成猜谜），**代价要说清**（调大它的开销看得见——
用量报表里有）。

**已经踩过的一个反例**：自动探测到的上下文窗口曾被写死压到 32768，理由是
「不封顶会让短上下文特化失去意义（配额永远用不完、截断永远不触发）」。
那是为了**验证我们自己的设计**，不是为了让活干得更好——远程供应商报 200K
时，我们按 32K 跑，能力被自己砍掉五分之四。现在探测值直接采用；想限制就
显式给 `--window`。

## 3. 总体架构

```
         ┌──────────────────────────────────────────────┐
         │  CLI 交互层                                   │
         │  交代任务 · 展示 diff · 授权确认 · 回滚        │
         └───────────────────┬──────────────────────────┘
                             │
         ┌───────────────────▼──────────────────────────┐
         │  Agent 主循环（调度者，不承担代码生成）        │
         │  取一步 → 装配上下文 → 问模型 → 校验输出 →     │
         │  分派/执行 → 更新状态 → 判断是否继续           │
         └──┬──────────┬──────────┬──────────┬──────────┘
            │          │          │          │
    ┌───────▼──┐ ┌─────▼────┐ ┌───▼─────┐ ┌──▼───────────┐
    │ 上下文    │ │  工具层   │ │  记忆层  │ │  代码索引层   │
    │ 装配器    │ │          │ │          │ │              │
    │  配额分配 │ │  文件读写 │ │  热记忆  │ │  符号表（树） │
    │  优先级裁剪│ │  代码搜索 │ │  冷记忆  │ │  引用图       │
    │  提示词模板│ │  命令执行 │ │  归纳器  │ │  相关性排序   │
    │          │ │  diff    │ │  检索器  │ │  仓库地图     │
    └───────┬──┘ └─────┬────┘ └───┬─────┘ └──┬───────────┘
            │          │          │          │
         ┌──▼──────────▼──────────▼──────────▼──────────┐
         │  模型网关 (llama.cpp HTTP)                    │
         │  /chat · /tokenize · /embeddings · 语法约束   │
         │  供应商抽象（多模态预留接口）                  │
         └───────────────────┬──────────────────────────┘
                             │
         ┌───────────────────▼──────────────────────────┐
         │  子智能体运行时（同模型 · 独立上下文 · 受限工具）│
         │  implementer · reviewer · distiller           │
         └───────────────────┬──────────────────────────┘
                             │
         ┌───────────────────▼──────────────────────────┐
         │  存储：SQLite(FTS5) · 热记忆文件 · 任务状态文件 │
         └──────────────────────────────────────────────┘
```

### 3.1 数据流：一次典型改动

1. 用户提出任务 → CLI 转交主循环。
2. 主循环建立任务状态，索引层产出 L0 仓库地图注入上下文。
3. 主循环判断改动规模：小改动直接处理；有实质逻辑则进入分派。
4. 分派器按结构化模板生成任务说明，交给实现者子智能体。
5. 实现者取用 L1/L2 级代码片段，产出修改，经授权后落盘。
6. 约束检查器运行，违反项回灌给实现者修正。
7. 审查者子智能体在**独立上下文**中，基于需求描述 + diff + 测试结果独立判断。
8. 主循环汇总结果，更新任务状态；必要时触发归档。

## 4. 模块设计

### 4.1 模型网关 `llm/`

| 模块 | 职责 |
|---|---|
| `client.py` | llama.cpp HTTP 客户端。封装 `/chat/completions`、`/tokenize`、`/embeddings`；统一超时、重试、流式输出。 |
| `budget.py` | token 预算计算。**直接调用服务端 `/tokenize` 精确计数**，不引入额外分词器。 |
| `providers.py` | 供应商抽象层。这是**多模态的预留接口**：新增供应商只需实现同一组方法。 |

关键决策是「语法约束解码」：llama.cpp 支持传入 GBNF 语法约束采样，使输出必然符合给定 JSON 结构。这从物理上消灭了格式错误，对 7B 级模型尤其关键——不再需要「格式错误，请重试」这类补丁，省下的上下文全部用于真实任务。

所有需要模型产出结构化内容的场合（工具调用、任务状态块、分派说明）都走语法约束。

### 4.2 上下文装配器 `context/`

| 模块 | 职责 |
|---|---|
| `assembler.py` | 按优先级与配额把各来源拼装成本轮上下文。 |
| `policy.py` | 超预算时的裁剪策略：从最低优先级开始砍。 |
| `templates.py` | 提示词模板，可版本化。 |

#### 分层配额（起始值，全部可调）

术语定义：**有效预算 = 模型上下文窗口 − 输出预留**。下文所有百分比均以有效预算为基数，输出预留不参与分配。

| 区段 | 占有效预算 | 说明 |
|---|---|---|
| 系统提示 + 工具定义 | 固定约 800 token | 尽量压缩，工具描述只保留必要信息 |
| 热记忆 | ≤ 15% | 硬上限，写满即触发下沉 |
| 任务状态 | 约 100 token | 结构化，非自由文本 |
| 检索结果 | ≤ 15% | 已经过归纳浓缩 |
| 当前代码片段 | ≤ 35% | 由索引层精确取用 |
| 最近轮次 | 余量 | 通常只需最近 1–2 轮 |
| **输出预留** | **≥ 15%，硬性** | 不参与分配 |

输出预留必须硬性保留：上下文接近满载时模型质量显著下降，且没有空间生成响应。这是 70%/90% 两条触发线存在的原因。

### 4.3 代码索引层 `index/`

**树负责定位，图负责影响分析。** 这两件事必须同时存在：包含关系天然是树，而跨文件引用在树上是两个不相干的分支，无法表达。

| 模块 | 职责 |
|---|---|
| `extract.py` | 用 Python 标准库 `ast` 提取符号：文件、类、函数、方法及其签名与行号。设计为可替换接口，后续可换 tree-sitter 支持多语言。 |
| `graph.py` | 构建引用边：定义、调用、导入、继承。 |
| `repo_map.py` | 相关性排序与压缩地图生成。 |

#### 分层加载

| 层级 | 内容 | 大致开销 | 何时加载 |
|---|---|---|---|
| L0 仓库地图 | 全部文件路径 + 各文件顶级符号名 | 300–800 token | 任务开始自动注入 |
| L1 文件符号表 | 某文件的类/函数，含参数与行号，不含函数体 | 50–150 token | 按需，或由相关性自动选中 |
| L2 符号实现 | 某个函数/类的完整源码 | 精确，通常数十至两百行 | 模型明确请求时 |
| L3 邻域 | 该符号的调用者、被调用者、同族符号 | 数十 token | 准备改动时自动带上 |

深度止于 L3。更深的层级收益递减而往返成本上升。

**定位链走 L0→L1→L2，找到即停。** 但「读取」与「改动」的取舍不同：一旦进入改动阶段必须补 L3，否则模型看不到自己会改坏谁。这不是为省 token 而做的选择，是正确性问题。

#### 自动预取，而非让模型摸索

若每一层展开都由模型决定，token 省了，但往返轮次暴涨——每一轮都是完整模型调用，代价远超省下的 token。而且**小模型极不擅长决定「下一步该查什么」**，它会反复查错方向。

因此分工为：任务开始时，检索器用任务描述中的关键词与符号名自动匹配，展开到 L1，把候选文件符号表直接放进上下文，让模型一眼看到「可能相关的有三处」；随后模型才用工具主动深挖到 L2/L3。

模型要做的判断从「我该查什么」降级为「这三处里哪个对」——后者它能胜任。

#### 增量更新

索引表以文件内容哈希为键。文件未改动则复用旧索引，仅重新解析变动文件。仓库越大收益越明显。

### 4.4 记忆系统 `memory/`

#### 三层结构

按**生命周期**切分，而非按主题。不同生命周期的信息，其注入时机、检索方式、淘汰策略完全不同，混在一个桶里只能靠相似度硬猜。

| 层 | 内容 | 存活期 | 存储 | 进上下文时机 |
|---|---|---|---|---|
| 工作记忆 | 当前任务即时状态 | 一次任务 | 内存 + 检查点文件 | 每轮 |
| 热记忆 | 项目事实、用户偏好、关键决策、教训、进行中 | 长期，容量硬限 | 单个 Markdown 文件 | 每轮全量注入 |
| 冷记忆 | 全部历史明细 | 永久 | SQLite | 按需检索 |

热记忆的容量上限定义为**有效上下文预算的 15%**，而非绝对 token 数——绝对值在换模型或改上下文长度后必须重调，百分比则不必。这个上限同时充当新陈代谢机制：写满即触发下沉，防止它逐步吞掉全部预算。

#### 热记忆文件格式

人类可读、可直接手工编辑。文件本身即是「项目当前认知状态」的快照。

```markdown
# 项目记忆（自动维护，也可手动编辑）

## 项目事实
- 依赖用 uv 管理；测试命令 `uv run pytest -q`
- 配置从环境变量读取，解析在 `config.py`

## 用户偏好
- 偏好小函数，拒绝超长的函数体
- 改动前先看 diff 再决定是否应用

## 教训
- [置信 0.8] 解析自定义格式时先上语法约束，不要用正则 —— 来源 ep#42

## 已知问题
- parser 的错误处理尚未统一

## 进行中
- 给索引层加增量更新
```

#### 记忆类型

| 类型 | 含义 | 示例 |
|---|---|---|
| `fact` | 项目客观真相 | 「测试命令是 `uv run pytest -q`」 |
| `preference` | 用户的习惯与偏好 | 「偏好小函数」 |
| `decision` | 做过的选择**及理由** | 「选 SQLite 而非向量库，因为要全文检索且不想引依赖」 |
| `episode` | 发生过什么 | 「09-11 重构 parser，把 `_scan` 拆成三个函数」 |
| `failure` | 试过但未走通的方案 | 「用正则解析该格式失败」 |
| `lesson` | 从失败提炼的可复用规则 | 「解析自定义格式时先上语法约束」 |

`decision` 必须连同理由记录——理由才是可复用的部分。只记「用了 SQLite」无用，记「因为要全文检索且不想引依赖」才能在遇到同类选择时产生价值。

#### 从失败到成长：三级台阶

记录失败本身不构成成长。成长必须走完三级：

1. **失败事件** → 存入冷记忆。作用是「下次遇到类似情况时能查到」。
2. **教训** → 提炼为可复用规则，存入热记忆。这是从「记录」到「规则」的跃迁。
3. **主动应用** → 在进入对应场景时把教训推到模型面前，而非等待检索偶然命中。

第 3 步是成长真正发生的地方。实现方式是把教训带上 `trigger`（场景关键词），一旦主循环进入匹配阶段（如「开始改代码」），自动注入相关教训。

#### 防止记忆污染

小模型总结出的教训可能是错的，而错误的教训会持续误导，比不学习更糟。约束如下：

- 每条教训必须附**来源编号**，可回溯到原始事件。
- 教训被应用后记录结果，有效则提升 `confidence`，无效则降低。
- 低于置信阈值的教训不进入热记忆，仅在检索时可能被命中。
- 定期清理长期未验证或验证失败的教训。

#### 检索策略

从便宜到贵三层兜底：

1. **热记忆直接注入** —— 零成本，故必须小。
2. **FTS5 全文检索** —— 毫秒级。**在代码场景下这是主力而非兜底**：讨论对象是 `parse_config`、`UserService` 这类独特标识符，关键词命中准确率远高于日常对话场景，通用 RAG 中「关键词不够用」的结论在此不成立。
3. **向量语义检索** —— 仅在前两层全军覆没时启用，后期按需实现。

候选结果按「相似度 + 时间衰减 + 使用频率」打分排序。

#### 独立归纳会话

检索结果不直接进入主上下文，而是交由独立的归纳会话处理：主循环提出需要了解什么（**可附带提示词**），归纳会话检索并以更大预算阅读原文，产出带来源编号的浓缩结论，只有该结论进入主上下文。

两个要点：

- 归纳使用**同一个模型、不同上下文**，不额外占用显存，代价仅为一次调用延迟。
- 归纳结果必须**可追溯到来源编号**，并明确标注为摘要而非原文；当结论涉及修改代码时，主循环应能顺着编号回看原文。这是防幻觉的必要措施。

### 4.5 工具层 `tools/`

| 模块 | 职责 |
|---|---|
| `registry.py` | 工具注册与 JSON Schema 校验。所有工具调用经此校验，拦截参数幻觉。 |
| `fs.py` | 读文件、写文件、列目录、按符号取片段。全部限制在项目根目录内。 |
| `search.py` | 基于 `rg` 的代码搜索。 |
| `exec.py` | 命令执行。白名单 + 超时 + 工作目录限制。 |
| `diff.py` | 生成修改预览、应用修改、回滚。 |
| `git.py` | 状态查询、提交、回滚。 |

工具集刻意保持小。工具越多，小模型的选择错误率越高。

#### 索引与按需展开

提示词里常驻的**只有索引**：名字 + 参数名 + 一句干什么，按类别分组。
完整的描述与参数含义放在 `tool_help` 后面按需取（传工具名、类名或 `*`）。

这是原则 2.2「精确取用，而非整份塞入」落到工具层。量出来的账：十五个工具的
整份说明 665 token，索引 210——**而它每个请求都要重述一遍**。同一批 50 道
回归任务里真正用到的只有 6 个工具，没被用到的那些每一轮都在收费。

两处细节不能省：

| 必须留 | 为什么 |
|---|---|
| 参数名 | 语法约束给的是「所有工具参数的并集」，不说哪个参数属于哪个工具；模型在写下调用之前，参数表只有这一处可见 |
| 「什么时候用」 | 那部分在工作方式的常驻文案里，不在工具描述里——收掉描述不等于收掉指引 |

子智能体的 `tool_help` 绑定的是**裁剪之后**的注册表：给审查者列出写工具的
说明，等于告诉它一件它做不到的事。

### 4.6 约束检查器 `check/`

把软要求翻译成硬反馈的装置。每次写文件后自动运行，违反项作为具体反馈回灌。

约束加在**函数级**而非文件级——决定小模型成功率的是它一次要生成和处理的最小单元，而这个单元是函数。

| 约束 | 说明 | 起始建议值 |
|---|---|---|
| 单函数行数 | 最直接的一条，等于模型一次连续生成的最长代码 | ≤ 40 行 |
| 参数个数 | 参数多则调用时错位概率陡增 | ≤ 5 |
| 嵌套深度 | 小模型在深层嵌套里失向更快 | ≤ 3 |
| 单文件符号数 | 影响文件内定位准确度 | ≤ 20 |
| 单文件行数 | **软约束，仅警告不阻断** | ≤ 600 行 |

文件行数之所以是软约束：在**读取**场景下，索引层能精确取到函数级，文件大小影响极小；仅在对**编辑**的影响上仍有意义。它更多是内聚性差的症状指标，而非病因。

**拆分不是越细越好。** 一堆各 3 行、仅被调用一次的函数会让模型跳五六次才能拼出完整逻辑，反而更差。因此除上限外还需下限：过短且仅被调用一次的函数应合并。

### 4.7 子智能体运行时 `agents/`

#### 角色与工具权限矩阵

| 角色 | 读文件 | 写文件 | 执行命令 | 检索记忆 | 写记忆 |
|---|---|---|---|---|---|
| 主循环 | ✓ | ✓（仅小改动，需授权） | ✓（仅测试） | ✓ | ✓ |
| `implementer` 实现者 | ✓ | ✓（需授权） | ✓（白名单） | ✓ | ✗ |
| `reviewer` 审查者 | ✓ | **✗** | ✓（仅测试） | ✓ | ✗ |
| `distiller` 归纳者 | ✗ | ✗ | ✗ | ✓ | ✓ |
| `supervisor` 督导 | ✗ | ✗ | ✗ | ✗ | ✗ |

督导与其他三个不同的地方：它**没有工具，也不在独立循环里跑**——它是一次
结构化调用（判断该不该续期、要不要改道、还是收手）。它的证据由循环交给它，
不是它自己去取。理由见 4.8「步数预算与督导」。

两条硬性规则：

**写者与验者必须是不同上下文。** 若同一智能体自己写、自己测、自己判定通过，测试就退化为自我确认。验证的价值来自视角独立。审查者拿到的是需求描述 + 改动 diff + 测试结果，**不包含写者的推理过程**——否则它只是在附和那个推理。

**审查者的工具集里没有写文件权限。** 它物理上无法通过改代码来掩盖问题，也不需要依赖自觉。

#### 分派协议

主循环的分派质量决定整个系统的上限。7B 模型撰写任务说明本身就不轻松，说明若含糊，实现者产出必然无效，且失败点从一处变成两处。

因此分派必须走**结构化模板**，且经语法约束强制输出：

| 字段 | 说明 |
|---|---|
| `goal` | 本次改动要实现什么 |
| `targets` | 涉及的文件与符号（由索引层提供，非模型臆造） |
| `constraints` | 必须遵守的结构约束 |
| `acceptance` | 验收标准，可执行的判断依据 |
| `out_of_scope` | 明确不要做的事 |

`acceptance` 为空则**不允许派发**。这是防止含糊分派的硬闸门。

#### 分派阈值

小改动不值得开子智能体：改常量、加日志走三个会话是纯粹的浪费。按改动规模分档——小改动由主循环直接处理，有实质逻辑的才分派。分档阈值是可调参数，需通过测量确定。

#### 与主循环的差异

子智能体的上下文预算可以**大于**主循环（见原则 2.4）。它不在关键路径上，慢一点无妨，但可以一次看更多内容。上下文写满时直接丢弃重启，代价仅为重派——只要主循环状态完好。

### 4.8 主循环 `agent/`

| 模块 | 职责 |
|---|---|
| `loop.py` | 单步编排：装配 → 请求 → 校验 → 执行/分派 → 记录 → 判定 |
| `state.py` | 任务状态的结构化表示与读取 |
| `session.py` | 会话生命周期与持久化 |

#### 任务状态

每轮结束时维护，以结构化形式存在，每轮注入，替代「携带历史对话」的需求：

```
目标: 给 parser 加增量更新
已完成: ①读 parser.py ②确认索引表结构
当前: 正在改 _parse_file
待验证: 改动后跑 pytest tests/test_parser.py
已排除: 整文件重解析（太慢）
下一步假设: 比较文件 mtime
```

约数十个 token 的精确状态。**状态更新不额外增加模型调用**——让它成为每轮输出的固定组成部分，反正每轮本来就要产出工具调用。该状态块同样经语法约束强制输出，否则小模型会时写时忘。

落盘位置：`.agent/tasks/<task_id>.json`，人类可读，崩溃后可恢复。

#### 上下文重置

**不采用压缩对话历史的做法。** 压缩保留了错误的抽象——主循环需要的不是叙事，而是状态；让模型把 14 轮对话压成一段话，必然丢失信息，且丢的常是关键约束。

触发线分两档：

| 阈值 | 动作 | 是否中断任务 |
|---|---|---|
| 70% | 软整理：把较早轮次浓缩为事件存入冷记忆，腾出空间 | 否 |
| 90% | 硬重置：清空上下文，仅保留系统提示 + 任务状态 + 热记忆 + 最近 1–2 轮，并按需重新检索 | 是（但状态不丢） |

因为状态已外置，重置后上下文直接回到小尺寸而任务进度完好。这是原则 2.1 换来的能力。

用「每轮更新状态」替代「定期压缩历史」：状态更新是增量的小成本，压缩是偶发的大成本（一次完整模型调用）。

#### 任务规模边界

「中小型任务」在此有精确定义：**一次能在一个上下文预算内跑完的单元**。超出则显式分解为多个子任务，每个子任务是一次独立运行，之间靠任务状态与记忆衔接。

#### 步数预算与督导

步数上限原本是硬截断：撞上即停，由用户自己 `--resume` 再跑一次。那等于把
系统的判断成本推给用户，还把一件事拆成两次对话——第二次还得从头理解一遍。

现在改为**按进展续期，由督导会话决定**：

| 触发 | 谁先反应 | 动作 |
|---|---|---|
| 同一个调用连续重复 | 机械层（提醒 → 不执行） | 参数一字不差时的第一道 |
| 重复升级到第 4 次 | 督导 | 续期 / 改道（把话直接发给主循环）/ 收手 |
| 连续 8 步只有查看、没有产出 | 督导 | 同上（盖住「每步换一个查询」的漫游） |
| 一轮预算用尽而任务未结束 | 督导 | 续期（默认）或说明为什么做不下去 |

督导是**一次结构化调用**，不是又一个子智能体：它不需要翻文件，需要的是判断。
证据是目标、任务状态、最近发生了什么、机械统计——**不含主循环的推理过程**，
否则它只会附和那个推理（与审查者必须独立同一个理由）。代价约等于主循环的一步。

两条线必须同时存在：督导会失败、也会看错，所以可检验的机械信号仍然先挡一道；
而机械信号只看得到「参数相同」和「多久没产出」，看不出「它其实在换着花样绕」，
那部分交给督导。**总步数上限仍然保留**，但它不再是任务预算，而是一条安全线——
没有它，一个卡住的任务能把 GPU 烧一整夜。

### 4.9 CLI 交互层 `cli/`

| 模块 | 职责 |
|---|---|
| `app.py` | 入口与命令解析 |
| `approval.py` | 分级授权：读操作自由，写操作先出 diff 再确认 |
| `render.py` | 结果、diff、状态的展示 |

分级授权规则：

- **读操作**（读文件、搜索、查询索引与记忆）：完全自由，不询问。
- **写操作**：默认不直接落到工作区，先生成 diff 预览，由用户决定是否应用。
- **命令执行**：限制在项目目录内，白名单命令，带超时。

选择此方案的理由：小模型出错率较高，若错误直接污染真实代码，用户会丧失信任并最终弃用；而「先看 diff 再应用」几乎零成本，既能在出错时一眼识破，又不打断思路，其 diff 本身也是极好的学习材料。

## 5. 数据结构

存储分为两类：结构化数据入 SQLite，人可读的状态入文件。

### 5.1 SQLite

```sql
-- 文件索引
CREATE TABLE file (
    id           INTEGER PRIMARY KEY,
    path         TEXT NOT NULL UNIQUE,
    lang         TEXT NOT NULL,
    content_hash TEXT NOT NULL,
    mtime        REAL NOT NULL,
    indexed_at   REAL NOT NULL
);

-- 符号表（包含关系构成树）
CREATE TABLE symbol (
    id         INTEGER PRIMARY KEY,
    file_id    INTEGER NOT NULL REFERENCES file(id) ON DELETE CASCADE,
    parent_id  INTEGER REFERENCES symbol(id) ON DELETE CASCADE,
    name       TEXT NOT NULL,
    kind       TEXT NOT NULL,      -- module | class | function | method
    start_line INTEGER NOT NULL,
    end_line   INTEGER NOT NULL,
    signature  TEXT NOT NULL,
    doc        TEXT
);

-- 引用边（调用/导入/继承关系构成图）
CREATE TABLE ref (
    src_symbol_id INTEGER NOT NULL REFERENCES symbol(id) ON DELETE CASCADE,
    dst_name      TEXT NOT NULL,
    dst_symbol_id INTEGER REFERENCES symbol(id),
    kind          TEXT NOT NULL    -- call | import | inherit | attr
);

-- 记忆
CREATE TABLE memory (
    id            INTEGER PRIMARY KEY,
    kind          TEXT NOT NULL,   -- fact | preference | decision | episode | failure | lesson
    scope         TEXT NOT NULL,   -- project | global
    text          TEXT NOT NULL,
    trigger       TEXT,            -- lesson 专用：何时该应用
    source_json   TEXT,            -- 来源引用，保证可回溯
    confidence    REAL NOT NULL DEFAULT 0.5,
    importance    REAL NOT NULL DEFAULT 0.5,
    created_at    REAL NOT NULL,
    last_used_at  REAL,
    use_count     INTEGER NOT NULL DEFAULT 0,
    applied_count INTEGER NOT NULL DEFAULT 0,
    success_count INTEGER NOT NULL DEFAULT 0
);

CREATE VIRTUAL TABLE memory_fts USING fts5(
    text, content='memory', content_rowid='id'
);

-- 事件流
CREATE TABLE episode (
    id          INTEGER PRIMARY KEY,
    session_id  TEXT NOT NULL,
    task        TEXT NOT NULL,
    summary     TEXT NOT NULL,
    outcome     TEXT,              -- success | fail | aborted
    started_at  REAL NOT NULL,
    ended_at    REAL
);

-- 会话
CREATE TABLE session (
    id            TEXT PRIMARY KEY,
    project_root  TEXT NOT NULL,
    model         TEXT NOT NULL,
    context_limit INTEGER NOT NULL,
    created_at    REAL NOT NULL,
    last_active   REAL NOT NULL
);

CREATE INDEX idx_symbol_file   ON symbol(file_id);
CREATE INDEX idx_symbol_name   ON symbol(name);
CREATE INDEX idx_ref_src       ON ref(src_symbol_id);
CREATE INDEX idx_ref_dst       ON ref(dst_symbol_id);
CREATE INDEX idx_memory_kind   ON memory(kind, scope);
```

## 7. 可测量指标

没有测量，前面所有参数都只是猜测。以下指标用于调参和验证设计假设。

| 指标 | 衡量什么 |
|---|---|
| 任务完成率 | 端到端有效性 |
| 每任务平均 token 消耗 | 短上下文设计是否真的省 token |
| 每任务平均模型调用次数 | 往返成本 |
| 检索命中率 | 该找到时是否找到（索引与记忆的共同指标） |
| 上下文重置次数 | 短上下文压力 |
| 约束违反次数 | 检查器是否被遵守 |
| **重复失败率** | **同一个坑踩两次的比例——成长的直接度量** |

配套需要一个小任务集（约 20 条代表性的中小型改动任务），用于回归测试。它本身也是项目资产，架构每有改动即可重跑。

## 8. 分阶段落地

每个阶段都应产出可运行、可观察、可验收的成果，不做「全部写完再调试」。

| 阶段 | 内容 | 验收方式 |
|---|---|---|
| 0 | 环境与骨架（**已完成**：git 仓库、uv 项目、包结构、设计文档） | 目录结构就位 |
| 1 | 模型网关 + 最小主循环 | 能连上 llama.cpp，读完一个文件并回答问题 |
| 2 | 工具层 + 分级授权 | 能读、搜、生成 diff；写操作需确认；能回滚 |
| 3 | 代码索引层（符号表 + L0/L1 + 增量更新） | 给定任务能自动定位到相关符号，并把地图压到目标 token 内 |
| 4 | 记忆系统（热/冷/事件/归档） | 重启后能回忆项目事实；热记忆写满能自动下沉 |
| 5 | 约束检查器 + 编程工作流 | 违反结构约束时能收到具体反馈并修正 |
| 6 | 子智能体（实现者 + 审查者） | 能完成一次「分派 → 实现 → 独立审查」的完整改动 |
| 7 | 归纳会话 + 教训机制 | 同一类错误第二次不再重犯（重复失败率下降） |
| 8 | 向量检索（可选） | 仅在关键词检索出现可复现的漏检时才做 |

阶段 0–3 是「能干活」的最小闭环；阶段 4–5 是「记得住、守规矩」；阶段 6–7 是「会分工、会成长」。

## 9. 明确不做的事

以下内容有意排除在范围外。它们都有预留接口，但不在当前计划内实现。

| 不做 | 原因 | 预留方式 |
|---|---|---|
| 多模态（截图/设计稿） | 7B 级视觉模型对复杂 UI 截图效果有限；图像会显著消耗本就紧张的显存与上下文，与短上下文的核心目标直接冲突 | `llm/providers.py` 供应商抽象 |
| 语义知识图谱（LLM 抽取语义边） | 抽取需要足够强的模型；代码改动即需重建，成本极高而边际收益不明 | `index/graph.py` 已支持确定性边，语义边为增量 |
| 向量检索库 | 代码场景关键词命中率已足够；未测量前无法判断其价值 | `memory/retrieve.py` 保留第三层接口 |
| tree-sitter 多语言解析 | 当前以 Python 为主；先验证「索引 → 排序 → 压缩」链路价值 | `index/extract.py` 为可替换接口 |
| 并行子智能体 | 单 GPU 单服务，不会真正并行，无收益 | 运行时接口不假设串行 |
| 服务化 / 多用户 | 纯自用学习项目，无此需求 | — |

## 10. 待验证的假设

以下判断尚未经过实测，需要在对应阶段验证。若被证伪，设计需相应调整。

1. **热记忆 15% 的预算占比**是否合适——需在阶段 4 用任务集测量。
2. **函数级约束的具体数值**（40 行 / 5 参数 / 3 层嵌套 / 20 符号）——需在阶段 5 测量。
3. **FTS5 关键词检索在代码场景的命中率**是否真如预期般足够——需在阶段 4 测量，这是「不引入向量库」这个决定的前提。
4. **小改动直接做的分派阈值**定在哪里——需在阶段 6 测量。
5. **子智能体带来的延迟增量**是否在可接受范围——单 GPU 串行执行，一个改动至少三次模型调用，需实测。
6. **语法约束解码对小模型格式合规率的实际提升幅度**——需在阶段 1 测量。
